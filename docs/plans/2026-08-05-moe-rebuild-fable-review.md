## 0. Executive verdict

The charter is directionally right and unusually honest about legacy failures — its "why this is a rebuild" claims survived a read-only forensic pass against the code (Appendix A): eight CONFIRMED, one *understated* (the launchers are 2,395 and 3,066 lines, not "roughly 2,000"), and one — the 899-passing/one-failing test baseline — left NOT VERIFIED (re-running the suite was out of scope for a read-only review, and the claim-hook failure is a known environment-sensitive slow-spawn flake, so that snapshot should be re-established in Phase 1 rather than trusted). Its three durable differentiators are real and have **no equivalent in any surveyed competitor or framework**: (1) approval bound to an immutable graph-revision hash, (2) daemon-enforced fenced leases with epochs, and (3) daemon-verified evidence receipts. Those three are the product.

Of the ten product decisions I verdict **7 KEEP and 3 CHANGE, 0 REJECT** (rule: CHANGE means the decision's one-line text should be amended before freeze; KEEP means the text stands and my conditions bind the implementation beneath it) — but several KEEPs carry binding conditions, and the sharper findings are five gaps the charter does not currently name:

1. **Fan-in integration is drawn as a solved box; it is the least-solved problem in the entire field.** No vendor has automated semantic integration of parallel agent work — Codex ships one PR per isolated task with no cross-task fan-in, `uzi` "rebases the winner," Claude Code agent teams tell users to avoid touching the same files, GitHub ships one-click conflict resolution for humans. Worktrees fix *mechanical* conflicts only; Cognition's documented failure mode (incompatible implicit design decisions between parallel agents) survives perfect file isolation. Fan-in needs a first-class integrator role and a semantic-conflict story, not a pipeline box. ([Cognition, 2025-06-12](https://cognition.com/blog/dont-build-multi-agents); [Cognition, 2026-04-22](https://cognition.com/blog/multi-agents-working); [Codex cloud docs](https://learn.chatgpt.com/docs/cloud))
2. **Budget containment has no measurement source.** The charter's budget envelopes (cost, time, tokens) are enforcement without metering: nothing in the design states where per-node token/cost numbers come from across `claude`/`codex`/`gemini` CLIs. Budgets that cannot be measured are fiction. This needs an ADR (provider usage APIs, wrapper-metered proxies, or honest wall-clock/attempt-count proxies) before Phase 4.
3. **Revision supersession semantics are undefined.** "Approval binds to an exact graph hash and becomes invalid if that revision changes" has no precedent — LangGraph's resume semantics are the opposite (resumed runs execute whatever graph is compiled now, with code change between runs treated as a hazard the developer must manage, not a bound contract). The charter never says what happens to running `ExecutionAttempt`s, held leases, and partially satisfied joins when a superseding revision is approved mid-flight. Without that spec, strict binding produces either wedged goals or de-facto mutable revisions. ([LangGraph durable execution](https://docs.langchain.com/oss/python/langgraph/durable-execution))
4. **Reviewer calibration is real, unbudgeted work.** Anthropic's measured result: a standalone skeptical evaluator is far more tractable than self-critique, *but* their evaluator initially talked itself out of real issues and had to be tuned against ground-truth examples, and criteria wording measurably warped output. "Independent review" is not a drop-in role prompt. Also: reviewers perform *better* with a deliberately clean context (diff + receipts + criteria), not the worker's trace. ([Anthropic harness design, 2026-03-24](https://www.anthropic.com/engineering/harness-design-long-running-apps); [Cognition, 2026-04-22](https://cognition.com/blog/multi-agents-working))
5. **Dead-end memory is missing.** Every Anthropic long-horizon success leans on a mutable record of *what failed and why* ("without them, successive sessions will re-attempt the same dead ends"). The charter's durable records carry plans, evidence, and decisions — nothing carries failures forward into the next attempt's context. ([Anthropic long-running Claude, 2026-03-23](https://www.anthropic.com/research/long-running-Claude))

One charter fact-check worth surfacing because it could have been embarrassing either way: the **2026 SQLite WAL-reset corruption bug is real and precisely documented** — found 2026-03-03, latent in every version 3.7.0 (2010) through 3.51.2, fixed in 3.51.3 (2026-03-13) with backports 3.44.6 and 3.50.7 ([sqlite.org/wal.html#walresetbug](https://www.sqlite.org/wal.html), [changes.html](https://www.sqlite.org/changes.html)); OpenAI pinned codex's bundled SQLite for exactly this fix ([openai/codex PR #27992](https://github.com/openai/codex/pull/27992)). Note the trigger precondition — two or more connections racing a write against a checkpoint — which converts directly into a design rule: the daemon is the *only* process that ever opens the database. Which SQLite version the chosen Node driver bundles is an open verification item for the packaging spike.

**Matrix conclusions.** (a) Worktree-per-task isolation is commodity — six products ship it; it cannot be the pitch. (b) Every product converges on the **branch/PR diff as the review unit**; a fan-in surface that is not PR-shaped fights universal muscle memory. (c) **Nobody ships a graph UI** — where a richer surface exists, the market chose kanban (Vibe Kanban, Devin Desktop's Agent Command Center, GitHub mission control). (d) Nobody has hash-bound approvals, fenced leases, or daemon-verified receipts — Moe's moat is governance, not orchestration mechanics. (e) The well-funded end isolates with VMs, not worktrees, because worktrees don't isolate runtime environment (ports, toolchains, network) — which is exactly why legacy Moe grew a shared-resource lease system. (f) The commercial warning is loud: the closest structural analog to Moe died with ~30k monthly active users (per press coverage of the shutdown) for want of a business model, and the money in this category is billed compute/ACUs/credits, not boards.

## 2. The five most important user journeys

These are the journeys the product lives or dies on, ordered by frequency of occurrence, not glamour. J1 is the wedge; J2 is the thesis; J3–J5 are the trust builders. They intentionally align with the Phase 1 golden scenarios and the benchmark suite so one investment serves all three.

### J1 — The Tuesday bug fix (single agent, zero ceremony)

The most common unit of work must be *cheaper than legacy Moe*, or the rebuild regresses the product on day one.

Yaron types a goal ("fix the stale-port crash in daemon discovery"), accepts the default single-node graph without ever seeing a graph editor, approves the agent's plan, watches one agent work, and accepts a diff backed by a green verification receipt.

**Acceptance criteria**
- Goal → approved plan in **≤ 3 human actions** (create goal; approve plan; accept result) on default policy.
- No graph-editing surface appears anywhere in the flow; the "graph" is a single node created implicitly.
- The result view shows: diff, daemon-verified receipt (command, exit 0, output digest), truth-class chips on every fact, and the exact base/head SHAs.
- Wall-clock overhead vs. running the same agent bare is within the benchmark's 10% single-agent bar.
- The whole journey is completable from the board projection without opening the graph canvas.

### J2 — The three-way feature (fan-out, join, integrate) — the flagship

A decomposable feature (API endpoint + UI + docs) fans out to three agents and comes back as one integrated, independently reviewed change.

The planner proposes a subgraph; the control room shows the *fan-out preconditions* as checked facts before asking for approval: write scopes disjoint (with the actual path sets), each child has machine-checkable acceptance criteria, budget fits the goal envelope. Yaron approves the expansion **once**. Three agents run in isolated worktrees; the join node waits; an integrator agent (fresh lease, integration-scoped context) merges, reconciles one **semantic-coherence finding** (the API and UI children assumed different error-payload shapes at their shared boundary — §4.4's conflict class, invisible to file isolation), and produces a single branch + diff; verification runs; an independent reviewer (clean context: diff + receipts + criteria, *not* worker traces) approves; Yaron accepts.

**Acceptance criteria**
- At most **one** human approval for the expansion under the manual default (child plans covered by policy unless risk class says otherwise); zero when the project has opted into risk-tiered auto-approval (Decision 5).
- The approval screen displays disjoint write scopes explicitly; if scopes overlap, the proposal arrives pre-serialized or with a dedicated integration node — never as a silent race.
- If any fan-out precondition fails (no oracle for a child, scopes overlap without a plan), the system visibly **refuses to fan out** and proposes the sequential alternative. Fan-out is never the silent default.
- Join progress (2/3 children accepted, 1 executing) is visible at goal level without opening children.
- Integration conflicts surface as a human-visible integrator finding — never auto-mashed, never `git add -A`.
- The final review's context contains the integrated diff, all child receipts, and acceptance criteria — and demonstrably not the workers' transcripts.
- Timeline reconstructs the entire fan-out/fan-in causally (who spawned what, which epoch, which revision hash) after the fact.

### J3 — Kill it and trust it (crash recovery)

Yaron kills the daemon (or the machine dies) mid-J2 with two children executing. On restart: integrity check passes, every lease is either renewed or marked `SUSPECT`, no node silently changed phase, in-flight attempts resume or restart *as new attempts* with prior progress notes attached, and anything unprovable is labeled `UNKNOWN` — never guessed.

**Acceptance criteria**
- Zero duplicate ownership after restart across 10k randomized crash schedules (benchmark bar).
- Every fact in the UI post-restart carries its truth class; nothing that was `AGENT_REPORTED` silently upgrades.
- Resume of a healthy in-flight node is **one click** (or automatic under policy), and resumption creates a traceable continuation, not a mutation of history.
- A corrupt record quarantines as `NEEDS_RECONCILIATION` with a visible queue and a recovery action per item — silent skip is a release-blocking bug.
- `doctor` distinguishes healthy / degraded / unknown-truth and says which records are why.

### J4 — The rejection loop (review → re-plan → re-approve)

The independent reviewer rejects the work with findings; the node flips to a linked revision cycle: new plan revision, delta re-approval, new attempt, re-review. The loop is bounded; the third rejection escalates to a human decision rather than looping forever.

**Acceptance criteria**
- Rejection findings are structured (finding → evidence → required change), persisted, and pre-loaded into the re-plan context.
- Re-approval is a **delta approval**: the human sees plan-revision diff, not the whole plan again; unchanged approved parts are visually stable.
- Approval invalidation is visible and explained ("your approval bound revision `a3f…`; superseded by `b71…` because…").
- Loop counter visible on the node; policy-bounded (default 3) with human escalation, mirroring legacy's hard-won reopen caps.
- Old attempts and old plan revisions remain readable forever; nothing is overwritten.

### J5 — The silent build and the stale ghost (fencing)

An agent runs a 40-minute test suite in silence. Nothing steals its node (no ownership loss on silence alone — legacy's most expensively learned lesson, commits `3d2cb16`, `b30fb6f`, `28a6588`). Separately, its lease expires and is reassigned under policy; the original process wakes up and tries to `step.finish` — and is rejected by epoch fencing, with the rejection visible in the timeline.

**Acceptance criteria**
- Lease expiry → `SUSPECT`, never silent revocation; the control room shows what policy is waiting for (renewal grace, human confirmation).
- Human options at `SUSPECT` are explicit: wait / confirm-revoke (reason required, scope-limited, audited) / extend.
- A command from a superseded epoch is rejected even though the old process is alive, with a stable error naming the successor lease — and the attempt is recorded, surfaced, and countable (it is a benchmark bar).
- The long-silent-but-alive agent completes normally: heartbeat renewal keeps presence without proving authority, exactly as the charter separates them.
- At no point can two sessions both believe they own writes to one node — including across daemon restarts (J3 × J5 interaction is a required fault test).

## 3. Graph / control-room information architecture

### 3.1 Structural principles

1. **The board is the default projection; the graph is a view.** Zero field evidence exists that humans want to author or monitor DAGs day-to-day (§1.1, conclusion c). Moe's graph is the *data model*; the default surface is a column/board projection of node phases (the legacy 5-column mental model users already have), with the graph canvas one toggle away and indispensable for J2/J3 moments: fan-out topology, join progress, critical path.
2. **Every fact wears its truth class.** `OBSERVED` / `AGENT_REPORTED` / `DAEMON_VERIFIED` / `HUMAN_APPROVED` / `UNKNOWN` render as visually distinct chips everywhere a fact appears. This is the signature UI element of the product — the thing no competitor has — and it is how "proof before completion" becomes visible rather than doctrinal.
3. **Every action is a contract command.** Buttons are generated from `nextAllowedCommands`; the UI has no privileged mutation path (charter invariant, kept). A disabled action always states which precondition fails.
4. **Approvals are diffs.** Nothing is ever approved from a summary alone: plan approvals show the plan; expansion approvals show the subgraph with write scopes and budgets; re-approvals show deltas (J4); acceptance shows the diff + receipts.

### 3.2 Surface map

- **Goals home** — goal list with per-goal: phase distribution sparkline, budget meter (spent/envelope), held/suspect badges, approvals-pending count. Entry point for everything.
- **Goal view** — three toggled projections of one data set:
  - *Board* (default): columns by node phase; cards show owner principal, lease expiry, truth-class of latest claim, held badge with blocker name.
  - *Graph*: DAG canvas; node color = phase, border = lease state, badge = held/suspect; critical path emphasized; join nodes show child progress (2/3); expansion proposals render as ghost subgraphs pending approval.
  - *Timeline*: cursored event stream, filterable by node/actor/type; every event links to its aggregate; this is the J3/J5 forensic surface.
- **Node inspector** (right rail, any projection): objective + acceptance criteria; phase machine with legal transitions; lease card (principal, epoch, expiry, renew history); plan revision + approval binding (hash, approver, validity); attempts list with per-attempt evidence receipts; findings; artifacts; blockers; the node's *dead-end journal* (Gap 5); `nextAllowedCommands` as buttons.
- **Approvals inbox** — global, badge-counted; each item is a diff-shaped decision (plan / expansion / acceptance / revocation) with risk class and what-happens-if-idle. The single place a human must watch. Approval fatigue is a named failure mode (§4.9): the inbox must batch trivially-safe items under policy rather than training users to click through.
- **Runs & leases** — fleet view: every active session/principal, its lease, epoch, last renewal, current node; `SUSPECT` items float to top with the J5 action set.
- **Resources** — queues per shared resource: holder (task-keyed), waiters in priority order, lease expiry, force-release (human, reason-required).
- **Evidence viewer** — receipt detail: argv, cwd, env fingerprint, exit, output digest (expandable tail), base/head SHAs, dirty-tree digest; a "re-run this recipe" command for reviewers.
- **Health / doctor** — integrity status, `NEEDS_RECONCILIATION` queue with per-item recovery actions, outbox depth, schema version, SQLite version check (≥ 3.51.3).
- **Settings / policy** — policy revisions as first-class inspectable records (they gate everything; they must be as auditable as the graph). Read-only in v1: edits land as reviewed policy-file changes the daemon loads (§7).

No free-form chat surface (charter: dropped, agreed — structured comments/handoffs/decisions/alerts only). No game-like metrics. ## 4. Failure modes and guardrails for multi-agent spawning

The charter asked specifically for fan-out risk treatment. Each mode below: what happens, the evidence it's real, and the guardrail stack (prevent / detect / recover).

**4.1 Runaway cost.** Multi-agent ≈ 15× chat tokens; a 16-agent fortnight ≈ $20k; early Anthropic versions spawned 50 subagents for trivial queries. *Prevent:* budget envelopes inherited on expansion (children cannot mint budget — charter, keep); effort-scaling rules in planner policy (explicit "1 agent, 3–10 calls for simple work" tiers, per Anthropic); value gate on fan-out. *Detect:* per-node cost telemetry (Gap 2 — must be designed) rolled up to goal meters; alert at policy thresholds. *Recover:* pause-goal command; budget-exhausted is a first-class node outcome routing to human decision, not a crash.

**4.2 Duplicated work.** Two subagents independently investigating the same thing (Anthropic); 15 agents re-implementing the same helpers needing a dedicated coalescing agent (C compiler). *Prevent:* expansion validation rejects sibling objectives without distinguishing scopes; write-scope disjointness forces the planner to actually partition. *Detect:* integrator explicitly checks for duplicated implementation across child diffs (it is in its role charter, not left to chance). *Recover:* dedup is integrator work product; recurring duplication across goals is telemetry that decomposition prompts need repair.

**4.3 Mechanical write collisions.** Two agents edit one file. *Prevent:* disjoint write scopes by default; overlap forces serialization or a dedicated integration node (charter, keep); scope enforced at lease grant and *re-checked at integration* (explicit changed-path attribution, never `git add -A` — charter, keep; legacy evidence Appendix A claims 9–10). *Detect:* runner records tree-diff paths per attempt; out-of-scope writes flag the attempt. *Recover:* out-of-scope changes are quarantined at integration (excluded from the integration branch, surfaced as a finding), not silently included; repeated violations by a profile feed policy.

**4.4 Semantic conflicts (the one worktrees cannot fix).** Both children compile, both pass their tests, and they embody incompatible design decisions (Cognition's Flappy Bird; the entire "don't build multi-agents" argument). *Prevent:* planner resolves ambiguity before spawn (Cursor's planner/worker lesson); shared constraints (interfaces, contracts, naming) written into every child's context package; keep fan-out width honest (the numeric defaults are challenged in §5.1). *Detect:* the **integration node is a first-class agent role** whose acceptance criteria include cross-child coherence, with authority to open findings; the goal-level verification recipe (not just per-child tests) is the oracle at fan-in. *Recover:* integrator findings route to a repair node or re-plan; this is expected work, budgeted in every fan-out goal, not an exception path.

**4.5 Same-bug convergence.** All children blocked on one upstream defect, each "fixing" it divergently — 16 agents, zero speedup (C compiler kernel task). *Prevent:* dependency edges for genuinely serial prerequisites. *Detect:* **circuit breaker**: N children failing verification with correlated signatures (same failing check/file) → scheduler auto-holds the fan-out and proposes serialization or re-decomposition. Legacy's reopen-cap auto-flip is the same reflex; generalize it. *Recover:* one repair node upstream; children resume after.

**4.6 Context fragmentation and lost decisions.** Children lack sibling decisions; successor sessions re-attempt dead ends. *Prevent:* context packages carry decisions-to-date and constraints; artifacts pass between nodes on the graph, not through chat (charter, keep). *Detect/Recover:* the **dead-end journal** (Gap 5): each attempt records approaches-tried/failed and why; successor attempts and re-plans receive it. Distill, don't dump: workers return condensed summaries (1–2k tokens per Anthropic's context doctrine), full transcripts stay retrievable but out of context.

**4.7 Shallow or captured review.** Self-praise is documented; evaluators talk themselves out of real findings until calibrated; criteria wording warps output. *Prevent:* reviewer independence enforced by lease policy (different principal — charter, keep); **clean-context review** (diff + receipts + criteria; never worker traces — Cognition 2026); review rubrics versioned as policy. *Detect:* calibration corpus with known-bad examples as part of Phase 1 test assets (this is the unbudgeted work of Gap 4 — name it in the plan); reviewer-outcome telemetry (catch rates vs later human rejections). *Recover:* human spot-audit path from the evidence viewer ("re-run this recipe").

**4.8 Join deadlock and re-entry bugs.** Cyclic re-activation is where graph schedulers break in practice (AutoGen's `_remaining`-never-zero stall). Moe's DAG moves the cycle into rejection/re-plan re-entry. *Prevent:* readiness is a pure function of durable records (events → readiness), property-tested for re-entry: rejection re-arm, expansion replacement, revision supersession, join-policy re-evaluation. *Detect:* scheduler invariant checks in the 10k-schedule harness (bar N-3, §6). *Recover:* a stuck join is diagnosable from the timeline (which precondition is unsatisfied is displayed, not inferred).

**4.9 Human-control overload.** Fan-out multiplies approvals; fatigue turns gates into rubber stamps (OpenAI's guardrail design explicitly balances safety against prompt fatigue). *Prevent:* risk-tiered approvals (OpenAI's low/medium/high tool-risk shape) as an explicit per-project opt-in (Decision 5): when enabled, policy auto-approves in-envelope, disjoint-scope, read-only expansions and humans see only scope/budget escalations and overlapping writes; under the manual default, precondition-checked one-glance approvals and inbox batching carry the load. One expansion = at most one approval (J2). *Detect:* approval-latency and rubber-stamp telemetry (time-to-approve distributions). *Recover:* policy tuning is a first-class, audited change.

**4.10 Stale or spoofed clients.** Caller-selected identity and fail-open ownership checks are legacy's confirmed holes (Appendix A, claim 3). *Prevent:* daemon-issued credentials; every mutation carries session + lease token + epoch + expected version, checked **inside the applying transaction**; no missing-identity path exists at all. *Detect:* rejected stale-epoch commands are recorded and surfaced (benchmark bar: zero *accepted*; the count of *rejected* is a health signal). *Recover:* J5's flow.

**4.11 Expansion abuse (scope/budget minting).** A child subgraph tries to widen write scope or exceed budget. *Prevent:* containment validation on `graph.propose_expansion` (charter, keep — with the width default amended per §5.1: acyclicity, scope ⊆ parent scope, budget ⊆ remaining envelope, depth ≤ 3, fan-out ≤ 6 by default, policy-raisable with reason). *Detect:* benchmark scenario 8 covers it; also alert on proposals that fail validation repeatedly (an agent fighting its box is a signal). *Recover:* stable rejection reasons teach the planner; humans can explicitly raise envelopes as an audited decision.

**4.12 False completion and self-termination.** "It is easy to see tests pass and assume the job is done"; an agent `pkill`ed its own supervision loop. *Prevent:* `DONE` requires daemon-run verification receipts (charter's core promise, keep — the runner executes the approved recipe; agent-attested output is never sufficient); supervisor survives agent process death (legacy already learned this). *Detect:* receipts bind exact commit SHAs and dirty-tree digest, so "passed on a different tree" is detectable. *Recover:* J3 resume machinery; premature-victory attempts simply fail their verification gate and loop through J4.

**4.13 Duplicate-delivery side effects.** Outbox relay is at-least-once; a replayed notification must not double-grant a lease, double-launch a CLI, or double-run integration. *Prevent:* every consumer idempotent, keyed by event sequence; commands idempotent by `commandId` (charter, keep). *Detect:* fault tests replay the outbox aggressively. *Recover:* by construction.

## 5. Product decisions: KEEP / CHANGE / REJECT

Labeling rule, applied uniformly: **CHANGE** means the decision's one-line text should be amended before design freeze; **KEEP** means the text stands as written and my conditions bind the implementation beneath it.

| # | Decision | Verdict |
|---|---|---|
| 1 | Local-first, single machine v1 | **KEEP** |
| 2 | Graph-native core with bounded dynamic fan-out/fan-in | **CHANGE** |
| 3 | One local web control room; JetBrains first thin adapter | **KEEP** |
| 4 | Transactional DB + hashed exports; no Git-tracked runtime state | **KEEP** (binding conditions) |
| 5 | Manual approval by default; policy/risk-based automation later | **CHANGE** |
| 6 | Structured handoffs/decisions/artifacts/notes in v1 | **CHANGE** |
| 7 | Read-only importer, temporary adapter | **KEEP** |
| 8 | Explicit integration command; no agent auto-stage/push | **KEEP** (strengthen) |
| 9 | Agents propose child graphs; Moe validates and schedules | **KEEP** (two required specs) |
| 10 | Orchestration authority + workspace isolation; host sandbox later | **KEEP** (honesty condition) |

**1. Deployment — KEEP.** Local-first is the correct v1 truth boundary and the differentiator against an all-cloud field. Two eyes-open notes: (a) the local-first orchestrator category has demonstrated zero willingness-to-pay (Vibe Kanban's shutdown; Conductor monetizes its *cloud* tier) — the commercial thesis, whatever it is, lives in governance/evidence/enterprise control, not the board, and that's Yaron's call, not an architecture problem; (b) keep the contracts remote-clean (the charter's adapter shape already does this).

**2. Core shape — CHANGE.** Keep the graph as the data model and the DAG stance (with the two-layer cycle argument made explicit in an ADR: cyclic reasoning inside a node's agent session; acyclic execution-order edges between nodes; retries as new attempts). Change the *execution posture*, which the charter leaves ambiguous enough to read as parallel-by-default. The evidence is unambiguous — both vendors' guidance, the skeptics, and the successful parallel runs all agree parallel writes work only under preconditions. Replace with: **"A goal is a linear chain of nodes by default. Fan-out of write-nodes requires, checked at validation time: (1) disjoint write scopes, (2) machine-checkable acceptance criteria per child, (3) budget fit. Absent any of the three, the scheduler refuses and proposes the sequential alternative. Read-only nodes (investigation, review, comparison) parallelize freely against a snapshot."** Additionally: the board projection is the default UI (§3.1), and a first-class integrator role exists at every fan-in (§4.4). This is not a retreat from the thesis — "one goal can *safely* fan out" is precisely what the preconditions operationalize; safety is the feature, width is not.

**3. Primary UI — KEEP.** One canonical web control room is right: a graph, timeline, evidence viewer, and lease topology need one implementation, and legacy's dual-plugin parity tax is confirmed pain (hand-copied lifecycle tables that already disagree — Appendix A, claim 6). JetBrains embed via JCEF with browser fallback matches JetBrains' own constraint docs. Condition: the board projection is the default view (Decision 2); the graph canvas must earn its moments.

**4. State — KEEP, with binding conditions.** (a) Pin bundled SQLite ≥ 3.51.3 (WAL-reset fix confirmed; verify what the chosen Node driver actually bundles during the packaging spike — codex had to pin explicitly); surface the version in `doctor`. (b) **Sole-process rule**: exactly one process opens the DB at a time. During operation that is the daemon, with plugins and tooling on its API; `doctor` — whose primary use case is a daemon that cannot start — may open the DB directly, read-only, only after verifying no daemon holds it. This eliminates the WAL-bug precondition (concurrent connections racing a write against a checkpoint) while preserving the charter's requirement that `doctor` diagnose health, degradation, and unknown truth offline. (c) Event-source selectively — lifecycle/lease/approval/evidence ledgers, plain tables for config — and ship event-schema versioning + upcasting in v1 (the empirically top-ranked failure mode of event-sourced systems is schema evolution). (d) Artifacts and command output by digest/reference only; never inline in events (LangGraph's 85%-bloat wound). (e) Presence signals (heartbeats, renewals) must not serialize behind the full command transaction path — give them a lighter write path or batching, with the write-amplification budget measured in Phase 2 (LangGraph had to invent async durability modes after shipping; design for it instead). (f) Scheduled hashed exports (not just on-demand) so humans retain a diffable, greppable history trail outside the binary DB — this is the one real regression from legacy's git-visible `.moe/` and it deserves a default-on answer (a deliberate amendment of the charter persistence section's "Export is explicit" sentence; the decision's own text stands, hence KEEP).

**5. Approval — CHANGE.** Manual-by-default is right and matches the field's convergence (plan-approval gates in Claude Code agent teams; editable pre-execution plans in Devin/Jules). The amendment: ship the risk-tiered, resumable approval *machinery* (OpenAI's tool-risk pattern) in v1 as an explicit, audited **per-project opt-in** rather than deferring all automation to "later" — the fan-out thesis multiplies approval events (§4.9), and a purely manual v1 either trains rubber-stamping or suppresses the product's core motion. Amended decision text: **"Manual approval by default for plans, expansions, and acceptance; risk-tiered policy automation available in v1 as an audited per-project opt-in; no global modes."** This single posture governs every other statement in this review (J2, §4.9, Decision 9b, v1 scope item 7). Add the J4 requirement: re-approvals are delta approvals, or approval fatigue will do to the rebuild what `SPEED`/`TURBO` did to legacy.

**6. Memory — CHANGE.** Keep the v1 scope (structured handoffs, decisions, artifacts, scoped notes; semantic retrieval later). Add one record type the evidence says is the single most load-bearing artifact for long-horizon work: the **attempt journal / dead-end record** — what was tried, what failed, why — attached per attempt, fed into successor attempts, re-plans, and integrator context (§4.6). Legacy has no first-class version of this and Anthropic's data says its absence directly causes repeated dead-end attempts across fresh sessions.

**7. Compatibility — KEEP.** Read-only importer with manifests/hashes and `NEEDS_RECONCILIATION` for ambiguity is right, and Phase 7's "ambiguous assignments are never activated" is the correct hard line. Not chasing legacy tool parity is correct — the legacy surface's value was its lessons, now encoded as scenarios.

**8. Git delivery — KEEP, and strengthen.** The best-evidenced decision in the charter: legacy's launcher-owned `git add -A` delivery produced a whole incident class (Appendix A, claims 9–10; the silent auto-commit failure was diagnosed twice). Explicit changed-path attribution + exact tree IDs + policy-controlled integration is right. Strengthen with two additions: (a) integration output is **PR/branch-shaped** — the universal review unit (§1.1 conclusion b) — so Moe composes with GitHub/CI instead of fighting muscle memory; (b) the integration command is also the **second fencing layer**: it verifies the epoch of the producing lease before accepting a worktree's output, so a stale ghost's work dies at integration rather than landing (files can't check epochs; the integration gate can).

**9. Graph authority — KEEP, with two required specs before Phase 4.** Agents propose, Moe validates and schedules — correct, and genuinely novel: LangGraph's Send-style fan-out ships with no budget/scope/policy gate anywhere in the surveyed field. The two specs the charter must add: (a) **supersession semantics** (Gap 3): when a new revision is approved mid-flight, define per-node disposition — untouched nodes continue under their leases (their subgraph hash unchanged), removed nodes' attempts are cancelled with evidence preserved, changed nodes' attempts run to a safe boundary then re-enter as new attempts under the new revision; approvals name the exact node set they invalidate. (b) **The approval-latency budget** (§4.9): under the manual default, an expansion approval must be a one-glance decision — the fan-out precondition checks (scopes, budgets, oracle presence) render as verified facts, and one expansion costs at most one approval; where a project opts into risk-tiered automation (Decision 5), in-envelope, disjoint-scope expansions auto-approve with a recorded reason. Either way, expansion-decision latency is measured (§6) — otherwise the immutable-revision machinery recreates the friction OpenAI documents and users route around it.

**10. Scope boundary — KEEP, with an honesty condition.** Orchestration authority + workspace isolation is the right v1 line; a host sandbox is real but separate work (OpenAI needed a custom OS-account/firewall design for Windows). The condition: **never describe worktree isolation as a security boundary.** It is filesystem/branch isolation for *cooperative* agents; write scopes are enforced at lease grant and integration, not by the OS; agents share the machine, network, and toolchain. The UI and docs say "workspace isolation," not "sandbox," and the threat model ADR states plainly that a malicious agent is out of scope for v1 (the spoofed-*client* threat, by contrast, is in scope and fenced — J5).

### 5.1 The numeric safety defaults (the charter asked for these to be challenged)

The charter proposes four concurrent agents per goal, graph depth three, and twelve children per expansion, as policy values. Same labeling rule applied:

- **Four concurrent agents per goal — KEEP.** Consistent with the only vendor guidance that states a number (Claude Code agent teams recommends 3–5 teammates, [agent teams docs](https://code.claude.com/docs/en/agent-teams)) and with the evidence that coding-quality wins come from depth (evaluator loops, one-feature-per-session) rather than width; the 16-agent compiler run was oracle-rich greenfield, the exception that earns a policy raise, not a default.
- **Graph depth three — KEEP.** Matches Claude Code's own subagent nesting default of 3; each level multiplies join, budget-containment, and supersession complexity; a proposal needing depth > 3 is nearly always a decomposition failure better handled by re-planning the parent than by deeper nesting.
- **Twelve children per expansion — CHANGE to six, policy-raisable with an audited reason.** Twelve is double what any cited source supports as a default: recommended team sizes are 3–5, Anthropic's documented overspawn failure (50 subagents for simple queries) argues for tight defaults with explicit effort-scaling tiers, and a 12-wide expansion under a 4-concurrent execution cap guarantees a long queue in which later children execute against a repository their earlier siblings have already changed — precisely the staleness the immutable-revision machinery makes expensive. Six still covers every benchmark scenario; per-file oracle-rich decompositions (compiler-style) are the legitimate case for raising it, per goal, with a reason.

## 6. Changes to the benchmark and release bars

The suite (8 scenarios) is well-chosen — it encodes the right regressions. Amendments:

**Add scenarios:**
- **S9 — Fan-out refusal.** A goal whose decomposition lacks a machine-checkable oracle for one child, or has overlapping write scopes: the system must visibly refuse fan-out and propose the sequential alternative (Decision 2's preconditions are only real if refusing is tested).
- **S10 — Same-bug convergence.** All parallel children fail verification with a correlated signature: the circuit breaker (§4.5) must hold the fan-out and propose serialization, within a bounded number of wasted attempts.
- **S11 — Mid-flight supersession.** Approve a revision replacing part of an executing graph: per-node disposition follows the Decision-9 spec; zero orphaned leases; zero commands accepted from attempts on removed or changed nodes past their disposition boundary (I8); timeline explains every disposition.
- **S12 — Outbox replay.** Aggressively duplicate/replay notification delivery: zero double side effects (lease grants, launches, integrations) — at-least-once delivery is only safe if this is tested.

**Amend bars:**
- *"Zero invariant violations across 10,000 randomized command/crash schedules"* — enumerate the invariant set in the release record, minimally: (I1) ≤ 1 active lease per node; (I2) no accepted mutation from a non-current epoch; (I3) node phase transitions only via legal edges; (I4) every `ACCEPTED` node has its required receipts and review; (I5) committed events are never lost or reordered per aggregate after restart/replay; (I6) parent phase always consistent with children + join policy; (I7) readiness is re-derivable from the event log plus the referenced `PolicyRevision` — policy is itself an event-sourced ledger, and no plain-table config may be a readiness input (drift check between projection and recomputation); (I8) supersession disposition holds: after a supersession commits, attempts on removed nodes accept no further command, attempts on changed nodes accept none past their declared safe boundary, and attempts on untouched nodes are atomically re-bound to the new revision (their node-subgraph hash unchanged). An unenumerated "zero violations" bar is unfalsifiable.
- *"At least 1.8× median wall-clock speedup on the decomposable benchmark"* — keep, with two riders: report the **token/cost multiplier** beside it with a declared ceiling (the charter says cost is reported; make the ceiling explicit — e.g., speedup must be achieved at ≤ 5× single-agent tokens, calibrated in Phase 8 against the measured baseline), and report **acceptance-rate parity** as the same gate (already implied; make it a number).
- *"No more than 10% wall-clock overhead on the deliberately single-agent benchmark"* — keep, and additionally bound **human interaction count** for J1 (≤ 3 actions): ceremony overhead is the regression risk users will actually feel, and wall-clock doesn't measure it.
- Add: **expansion-decision latency** — p95 time from `graph.propose_expansion` to schedulable children, measured separately for the policy-auto path (target: seconds) and the human path (measured, not gated). A policy-gated system can pass every existing bar and still feel dramatically slower than ungated competitors on fan-out-heavy work; measure the tax honestly.
- Add: **presence-write headroom** — heartbeats/renewals at 4-concurrent-agent load must not degrade command p95 beyond the 500 ms UI bar (the write-amplification condition of Decision 4e, made falsifiable).
- Add: **stale-epoch rejection visibility** — S7's zero-accepted bar stands; additionally, every *rejected* stale command must be present in the timeline (silent rejection hides the exact forensics J5 exists to provide).
- *Release record additions:* the SQLite bundled-version check (≥ 3.51.3) in `doctor`; the reviewer calibration corpus exists with a measured, *reported* catch-rate on known-bad examples (Gap 4; gating on the number is deferred until a baseline exists); benchmark cost/speed results published per scenario, per the charter's own "speed gained only by unbounded spend does not pass."

## 7. Recommended v1 scope and explicit non-goals

### v1 in scope

My additions to the charter's scope are not free, so they come partitioned: **correctness-blocking** (supersession spec, S12 outbox idempotency, the enumerated invariant set, SQLite pin + sole-process rule) — non-negotiable, they guard invariants; **minimal-form in v1** (cost telemetry = ADR + capture-where-the-provider-exposes-it, attempt journal = a plain structured record with no retrieval machinery, integrator = a role profile + lease policy rather than new engine machinery, risk-tier automation = default-off policy); **deferred until telemetry demands** (calibration catch-rate as a *gate*, anything semantic-memory shaped). Offsetting cuts from the charter's implied v1: the **gemini provider adapter** (Claude first, codex second to prove the adapter seam — the JetBrains-first discipline applied to providers) and the control room's **policy editor** (policy is read-only in the UI in v1; edits land as reviewed policy-file changes the daemon loads). Net: v1 still grows by roughly four deliverables, and J1's ≤ 3-actions / ≤ 10%-overhead bars are the regression tripwire that keeps that growth honest.

1. **Transactional core** (Phases 2–3 as chartered): SQLite ≥ 3.51.3, sole-process daemon access, atomic event + projection + outbox, command idempotency, selective event sourcing with versioned events + upcasting, scheduled hashed exports, quarantine + doctor.
2. **Identity and fenced leases**: daemon-issued credentials, no missing-identity path, epoch fencing checked in-transaction on every mutation path (tools, plugin WS, force actions, importer), `SUSPECT` flow, human-privileged scoped revocation.
3. **Graph engine**: immutable revisions with hash-bound approvals, **supersession spec implemented** (Decision 9a), linear-chain default, fan-out behind the three preconditions with refusal as a first-class outcome (S9), read-only parallel nodes, join policies, circuit breaker (S10), depth/width/budget policy limits.
4. **Runner and evidence**: isolated worktrees with exact base SHA, provider adapters (Claude first, codex second; gemini deferred post-v1), explicit changed-path attribution, daemon-executed verification recipes, receipts, **attempt journal / dead-end records** (Decision 6), context packages with digests.
5. **Integration as a role**: integrator lease at every fan-in, PR/branch-shaped output, epoch verification of producing leases, semantic-coherence findings, no auto-merge of conflicts.
6. **Independent review**: separate principal, clean-context inputs (diff + receipts + criteria), versioned rubrics, calibration corpus, bounded rejection loops with delta re-approval.
7. **Control room**: board default + graph + timeline projections, node inspector, approvals inbox with risk-tiered auto-approval (per-project opt-in, default off — Decision 5), runs/leases, resources, evidence viewer, health/doctor — all over generated contracts; truth-class chips everywhere.
8. **Protocol**: one generated command/query contract; official MCP TS SDK (stdio + Streamable HTTP); cursored event stream; loopback default.
9. **JetBrains thin adapter** (start/discover daemon, embed control room, external-browser fallback) and **read-only legacy importer** with reconciliation report.
10. **Cost telemetry ADR and minimal implementation** (Gap 2): per-attempt token/cost capture where the provider exposes it, declared proxies where it does not, rolled up to node/goal budget meters — budgets enforce only what this measures.

### Explicit non-goals for v1

- **VS Code parity** (thin adapter post-stability, per charter — hold that line; legacy evidence says workers over-index on VS Code).
- **Free-form agent chat**, game-like metrics, rail proposals, `SPEED`/`TURBO` globals (charter, agreed).
- **Cloud sync, remote/team deployment, multi-machine scheduling.**
- **Host-level sandboxing / malicious-agent containment** (Decision 10's honesty condition; a later defense layer).
- **Automated semantic merge.** The integrator *surfaces and resolves with agency*, it does not promise conflict-free auto-fan-in; nobody in the field has this and v1 must not claim it.
- **Semantic/vector memory retrieval** (structured records first; retrieval when evidence demands it).
- **ACP (Agent Client Protocol) support** — evaluate during Phase 5 as a candidate future adapter surface (the field is standardizing on it: Devin Desktop, multiple CLIs), but do not build it into v1; MCP + provider adapters suffice.
- **Legacy write-back or dual writes** (charter, agreed — import is one-way, legacy stays rollback-readable).
- **A mobile/monitoring surface**, multi-user RBAC beyond the single-owner model, and marketplace/plugin ecosystems.

### The one-sentence product position this scope supports

Every competitor can run parallel agents; none can *prove* what their agents did, *bound* what they may do, or *refuse* parallelism when it would be unsafe — Moe v1 is the local control plane that does exactly those three things, with the evidence visible on every card.
