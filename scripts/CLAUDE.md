# scripts/CLAUDE.md

Agent launcher detail (`scripts/moe-agent.{sh,ps1}`, `moe-team.{sh,ps1}`). Project overview, build and test commands: root `CLAUDE.md`. Keep `.sh` and `.ps1` in string parity (`bash scripts/tests/parity-check.sh`). Keep `moe-agent.ps1` saved as UTF-8 with a BOM: Windows PowerShell 5.1, which the JetBrains plugin uses for native Windows seats, reads a BOM-less script as ANSI and cannot parse its non-ASCII text (the parity check enforces it).

## Per-CLI launch

`grok` (xAI Grok Build) follows the same role-based polarity: headless is `--prompt-file <temp file> --yolo --cwd <project> --no-auto-update --output-format plain` (the per-iteration prompt travels through a temp file — grok reads no stdin and has no `--prompt` flag), interactive passes a short pointer prompt positionally, and `-GrokExec`/`--grok-exec` forces headless; auth is `XAI_API_KEY` or a cached `grok login` (`~/.grok/auth.json`; a non-fatal `[WARN]` when both are missing). `codex` runs the interactive TUI for every role by default (a TUI seat lands its commits only when the operator closes the TUI, so opt a seat into one-shot headless with `-CodexExec`/`--codex-exec` when per-task landing matters); headless is `codex -c <per-seat overrides> -c approvals_reviewer=user exec -C <project> --sandbox <MOE_CODEX_SANDBOX, default danger-full-access>` — **never `--full-auto`**: codex-cli 0.147+ rejects it with exit 2 before any work and the wrapper relaunch-loops (the standalone codex installer auto-updates, so any seat can hit it); `exec` already implies `approval_policy=never` and the reviewer pin keeps that even under an operator `approvals_reviewer = "auto_review"`, `MOE_CODEX_SANDBOX=inherit` omits the flag (read-only when no config sets `sandbox_mode`). The default is full access, not `workspace-write`, because codex 0.148+ refuses every un-annotated MCP tool (all of `moe.*`) under `never` + any sandbox (`MCP tool call requires approval, but approval policy is never`) and the Windows unelevated sandbox (`[windows] sandbox = "unelevated"`) cannot spawn a Store-installed pwsh (`CreateProcessAsUserW failed: 5`; `codex sandbox -- <cmd>` reproduces it offline) — the config writer also pins `default_tools_approval_mode = "approve"` on the moe/serena servers so an explicit `workspace-write` keeps MCP working (without `[windows] sandbox` at all, `workspace-write` silently runs read-only on Windows). `parity-check.{sh,ps1}` fail on any `--full-auto` reintroduction. Before the first headless launch the wrapper probes the real argv plus `--help` once per process; a codex that rejects a flag stops the seat with `MOE_CLI_ARGV_REJECTED` + a `#general` escalation instead of relaunch-looping (`MOE_DISABLE_ARGV_PROBE=1` skips it). Model defaults: `claude-opus-5-5` for every role (launched with `--effort max`; a claimed task's `launch` hint from `claim_next_task` sets that session's effort, and its model unless the operator pinned one), honored only by the `claude` CLI; codex instead gets `model_reasoning_effort = "xhigh"` written into its config.toml (override via `MOE_CODEX_REASONING_EFFORT`), and a claimed task's `launch.codex` hint adds per-launch `-m <model>` and `-c model_reasoning_effort=<effort>` on both the TUI and `exec` paths (the argv probe included) — the operator pin wins (`--model`/`settings.models.{role}` for the model, `MOE_CODEX_REASONING_EFFORT` for the effort); grok gets `-m` only when a model is explicit (`-Model`/`--model`, `settings.models.{role}`, else `MOE_GROK_MODEL` — never the claude fallback) and `--effort` only from `MOE_GROK_EFFORT`; override the claude model via `-Model`/`--model` or `settings.models.{role}`.

## Wrapper behaviour

- **Land on every exit** (`scripts/moe-agent.{ps1,sh}` post-flight — the wrappers are the Git-write actors; the daemon is state-only: it never writes git state, lands, pushes or runs the gate, and its Git reads are the status fingerprint for handoff notes plus bounded cached-ref affected-path validation (no fetch or checkout)). With `settings.autoCommit` on (default) every session exit that holds a task lands its bytes. A **worker** exit at `REVIEW`/`DONE` makes a *completion* commit (`feat|fix(task-<id>): <title>`) and pushes; any other exit (WORKING/BLOCKED/PLANNING/AWAITING_APPROVAL, or a failed status lookup → `status=UNKNOWN`) for worker/architect/qa makes a *checkpoint* commit (`wip(task-<id>): … [status=<S> role=<r> cli-exit=<N>]`; pushed per `settings.checkpointPush`, default on; off via `settings.checkpointCommits=false` or `MOE_DISABLE_CHECKPOINT=1`). Attribution is per task and pathspec-only (`:(literal)`; never `git add -A`/`-u`, never a bare `git commit` against the shared index, no whole-tree fallback): a per-task baseline snapshot (`<gitdir>/moe/baseline/<taskId>.tsv`, taken at pre-flight, pruned after each landing, kept until DONE/ARCHIVED) plus `moe.get_commit_scope` tier every dirty path — **ASSERTED** (completed-step `modifiedFiles`, `declare_files`, prior commits — `declare_files` paths committed regardless of baseline unless DENY or CONTESTED holds them, the rest only when this task produced the dirty bytes: tool-written, changed since the landing session's pre-flight snapshot (`P` rows; a crash recovery uses the dead session's), or carried as its own from its previous session (`C` rows) — else `MOE_ATTR_ASSERTED_FOREIGN`), **PLANNED** (plan-declared; only if changed since baseline), **TOOL** (supported Claude editing calls with matching successful `tool_result` events, and a `codex exec` seat's `--json` events: each path of a completed `file_change` and a successful Serena editing `mcp_tool_call` under the same per-tool rules, harvested by `scripts/prompt-cache-witness.mjs`; a Codex TUI, Gemini, Grok or interactive Claude session leaves none; declarations and completed-step reports remain ASSERTED), **MEASURED** (undeclared + changed; committed only when `attribution.undeclared` allows — default `'solo'` = no other live worker — else reported as `MOE_ATTRIBUTION_UNRESOLVED`), **PEER** (`MOE_ATTR_PEER_DECLARED` skip), **CONTESTED** (an own path another nonterminal task also declares, per `attribution.contested`: the default `skip-untouched` first holds it as `MOE_ATTR_CONTESTED_EDITING(task-<peer>)` while a contesting task is mid-step on it (an IN_PROGRESS plan step naming the path with an active session, `get_commit_scope` `editingTaskIds`; the disk fallback counts any IN_PROGRESS step), even when this session's editing tool wrote it, then lands it only when this session's supported editing tool wrote it, or when it was clean at this session's pre-flight and every contesting task is idle, else holds it as `MOE_ATTR_CONTESTED_UNTOUCHED(task-<peer>)`; `skip` holds it as `MOE_ATTR_CONTESTED` whatever the tools did; `commit` lands it; an older daemon without `editingTaskIds` lands as before; only a landed one carries a trailer, one per path naming every contesting task (`Moe-Contested: <path> (task-<a>, task-<b>)`), and `moe.record_commit`'s `contested` list has one row per (task, path). A `declare_files` entry never releases a hold, idle peer or not: a path dirty at pre-flight can carry the peer's hunks. The session-ended line names each held path `held=<path>(task-<peer>)` (five, then `+N more`) followed by one `MOE_CONTESTED_HELD remedy:` (a clause per held kind), and `moe.record_commit` alerts `#governors` with the same remedy. Under `skip-untouched`, verify the bytes are this task's and coordinate any live peer, then either the assignee's own session edits the path with a wrapper-observed editing tool (a shell write leaves no witness) or the stale peer task is legitimately completed or archived; an EDITING hold first waits for the peer's step to finish (then re-edit), or the peer's own landing carries the bytes; under `skip` only the peer route works. Never weaken the policy, auto-archive a peer or hand-land the path as the fix), **PREEXISTING** (`MOE_ATTR_PREEXISTING` skip — dirty before the task and untouched is never committed), **DENY** (`MOE_ATTR_EXCLUDED`: `.moe/**` except BOARD, `.mcp.json`, `.codex/**`, `.gemini/**`, `.grok/**`, `.claude/agents/**`, `.worktrees/**`, `attribution.exclude`), **BOARD** (own `.moe/tasks/<id>.json`). Landing = temp index + `commit-tree` + `update-ref` CAS (3 attempts; `MOE_COMMIT_FAILED_REF_CONTENTION` after), so peers' staged entries survive and git hooks do **not** run unless `settings.commitHooks=true` (then completion hooks run with a private index and detached HEAD; only the validated tree/parent reaches the branch CAS, and hook failure, tree mutation, signing/author configuration mismatch, or unborn HEAD refuses landing with rescue; checkpoints stay plumbing). Gate-failed (`settings.qualityGate`, epic-final by default, `MOE_DISABLE_QUALITY_GATE=1` skips), peel-failed, commit-failed, ref-contention and Ctrl+C teardown never touch the branch: the bytes go to a **rescue ref** `refs/moe/rescue/<taskId>/<utc-ts>` (`MOE_RESCUE_REF` chat line; never pushed), the baseline is kept, and the next pre-flight of that task lands it as a checkpoint (`MOE_CHECKPOINT_RECOVERED`) — except under the strong profile (verified-local, read from the task's attempt record or receipt journal, never the environment), where every checkpoint landing, recoveries included, is refused (`MOE_COMMIT_REFUSED_STRONG_CHECKPOINT`: no commit, ref, rescue ref or index entry is written) and the bytes and baseline stay for the verified completion. Refusal codes `MOE_COMMIT_REFUSED_NO_OWNED_PATHS` / `MOE_COMMIT_REFUSED_OWNED_PATH_MISSING` keep their meaning; `MOE_COMMIT_NOTHING_TO_COMMIT` is the idempotent no-op. Under the strong profile a completion moves the target only through its receipt journal `<gitdir>/moe/receipt/<taskId>.json`, made durable before `update-ref` (CQ-V07/V08): no frozen candidate of the landed tree, or no pinned attempt and plan revision, refuses it as `MOE_COMMIT_REFUSED_INTENT_INCOMPLETE`, a journal that cannot be made durable as `MOE_COMMIT_REFUSED_INTENT_UNWRITABLE`, and an earlier landing's journal still on disk as `MOE_COMMIT_REFUSED_UNRECONCILED_INTENT` (none writes a ref, rescue ref or push; the bytes and baseline stay); the attempt stays `finalizing` until the receipt is recorded (`MOE_FINALIZE_DEFERRED_RECEIPT`, settled by a pre-flight replay); and a landing whose commit on the target does not carry the verified tree (a rebase) is never adopted as proof (`MOE_DELIVERY_PROOF_NOT_TRANSFERRED`; `MOE_PUSH_REBASE` is ignored). **Owner guard** (`landing_owner_guard` / `Get-MoeOwnerGuard`; runs first in the post-flight landing, the pre-flight recovery — on a fresh scope — and the teardown rescue): a session that is not the task's assignee (an architect whose planned task a worker took, a QA seat whose row moved on) lands none of the task's bytes, source or BOARD, while the owner is protected — `get_commit_scope.assigneeProtected: true`, a registered non-DEAD seat or one holding an open attempt (`assigneeAlive` is display presence, never proof of death) — or while another seat's attempt on the task is still `finalizing` (`complete_task` clears the assignee before that seat's wrapper lands): `MOE_COMMIT_REFUSED_ACTIVE_ASSIGNEE`. Only a JSON `false` clears a foreign owner; an absent or non-boolean answer (an older daemon), a missing or malformed owner, a failed check or the disk fallback refuses as `MOE_COMMIT_REFUSED_OWNER_UNKNOWN`. A refusal moves nothing (no commit, ref, rescue or push; tree, shared index and baseline untouched), records `outcome: refused` with its code and no path fields, and ends the session line `commit=none … outcome=refused code=<code>`; the owner's own landing then commits those bytes. The assignee itself, an unassigned task, and a dead or absent owner (`assigneeProtected: false`) with nothing finalizing land as before, so orphan recovery is unchanged. The scope read and the branch CAS are two steps, not one atomic check. Every outcome is reported via `moe.record_commit` into `task.commits`. Branch safety: never commit on `main`/`master`/detached — peel onto literal `settings.consolidationBranch` else the shared `moe/work-<YYYY-MM-DD>` (not branch-per-task; existing non-default branches are reused).
  **Agent Git-write guard:** every CLI launch inherits a temporary, process-only `includeIf.gitdir`/`core.hooksPath` overlay for the exact control checkout. Ordinary agent/subagent `git commit` and `git push` fail with `MOE_AGENT_GIT_REFUSED: the wrapper lands the work`, including after a failed scratch `cd`. Separate repositories and linked worktrees keep their own hooks. No installed hook or persistent Git configuration is changed: other hooks delegate to their original absolute files. The wrapper/sidecars never inherit this overlay; completion/checkpoint landing and `settings.commitHooks` semantics are unchanged. Setup/identity/configuration/permission validation failure stops launch with `MOE_AGENT_GIT_GUARD_FAILED`; non-Git projects launch without claiming protection. This is an accidental-write guard, **not a malicious-agent sandbox**: `--no-verify`, explicit `core.hooksPath`, or stripping inherited Git configuration can bypass it. A human-only, one-command override (with restoration) is documented in [Troubleshooting](../docs/TROUBLESHOOTING.md#agent-git-write-refusal); agents must not use that override to repair landing. Use `cd /absolute/scratch && git ...` or `git -C /absolute/scratch ...`, never continue Git commands after a failed `cd`.
- **Land on every exit, worktree mode** (`settings.worktreeMode: 'on'`; the same wrappers land, and the daemon still never writes git state). A worker on a worktree-mode claim works in, and lands from, its own task worktree W on `moe/task/<taskId>`; the shared-mode baseline, tiers, peel and `moe/work-<date>` above do not apply to it. Completion runs the design's steps L0-L14 (`docs/plans/2026-10-30-per-task-worktrees.md` §2.2). Flip-on, rollback and the doctor probes: [Troubleshooting](../docs/TROUBLESHOOTING.md#worktree-mode).
  - **Scope.** The daemon pins the mode per attempt (`workspaceMode`), and only a WORKING claim gets `worktree`. A worker reads it from the claim's `workspace`, else from a pre-flight `get_context` whose `task.id` is the claimed task; on such a reply a missing `workspace` means shared. With neither (a failed, empty or foreign read) the mode is unknown: shared mode as before, except on a control checkout on `moe/control`, where the seat stops with `MOE_WORKTREE_CONTEXT_FAILED` (one `moe.report_blocked`, no CLI; unblock the task once `get_context` answers). A worktree-mode claim with no context read stops with the same code. A control checkout is in worktree mode only while its HEAD is `refs/heads/moe/control` (`control_worktree_mode` / `Test-MoeControlWorktreeMode`); any other HEAD is shared mode, unchanged.
  - **Provisioning** (worker pre-flight, `provision_worktree` / `Initialize-MoeWorktree`, before any CLI). W = `<git top>/.worktrees/<taskId>` on `moe/task/<taskId>`: locked, sparse (`'/*' '!/.moe/'`, so W never holds `.moe/`), cut from the target (origin's in remote mode, fetched first; a failed fetch warns `MOE_LAND_FETCH_FAILED` and cuts from origin's target as last fetched), reused by later sessions and re-added on an existing branch. The pre-flight first switches the control checkout to `moe/control` when its HEAD sits at the target's commit. Each guard stops the seat with one `moe.report_blocked`, launches no CLI and never falls back to the shared checkout: `MOE_WORKTREE_UNSUPPORTED_GIT` (git older than 2.38), `MOE_WORKTREE_PROJECT_NOT_TOP`, `MOE_CONTROL_NOT_FOLLOWING` (the control checkout is not on `moe/control`), `MOE_WORKTREE_MODE_MISMATCH` (a recorded task commit on another ref that the target lacks, or a shared-mode claim whose `moe/task/<taskId>` holds bytes HEAD lacks), `MOE_WORKTREE_PATH_TOO_LONG` (Windows: over 240 characters without `core.longpaths`), `MOE_WORKTREE_MOE_PRESENT` (`W/.moe` exists) and `MOE_WORKTREE_CREATE_FAILED` (the target is not a local branch, or an add, repair, sparse checkout or config write failed). `MOE_WORKTREE_CONFIG_RETRY` is an info line while another git process holds `.git/config` (5 tries).
  - **Launch** (`prepare_worktree_launch` / `Initialize-MoeWorktreeLaunch`). Every CLI runs in W, the PowerShell `claude` launch included; `MOE_PROJECT_PATH` stays the control checkout, and `MOE_WORKTREE_PATH`, `MOE_TASK_BRANCH` and `MOE_LAND_TARGET` are exported. The MCP and per-CLI configs and the subagent mirror are written into W. Serena's root is W (its `.serena/project.yml` named `<name>@<taskId>`), and `W/.serena/memories` and `W/.claude/skills` link to the control checkout's, each recorded first in the manifest `<common gitdir>/moe/worktree/<taskId>.links`. `MOE_WORKTREE_SERENA_OUTSIDE`, `MOE_WORKTREE_LINK_FAILED` (Serena is off for the launch when the memories link fails) and `MOE_WORKTREE_DEPS_MISSING` (a `package-lock.json` directory without `node_modules`) are warnings; a failed config write stops the seat with `MOE_WORKTREE_CREATE_FAILED`. A wrapper copy inside `.worktrees/task-*` refuses to start (`MOE_WRAPPER_IN_WORKTREE`): seats run only the control checkout's committed wrapper. So in a task worktree, edit `scripts/moe-agent.{sh,ps1}` in place with a TOOL-witnessed editor, then run `bash -n` or ParseFile; the atomic-save rule under **Hot reload** applies only to the shared or control checkout's copy.
  - **Attribution in W.** No baseline and no tiers: every dirty path in W lands except DENY (`MOE_ATTR_EXCLUDED`). DENY is `denied_wt` / `Test-MoeDenyPathWorktree`: the shared DENY list without its BOARD exception (so all of `.moe/**`), plus `.claude/skills/**` and `.serena/project.yml` (the launch's link and rewrite). The control checkout's dirt is listed at pre-flight; a path dirtied there during the session prints `MOE_WORKTREE_STRAY_EDIT` and gets one task comment, and is never landed or reverted (a human decides).
  - **Checkpoints** (L0-L2, `land_worktree_checkpoint` / `Invoke-MoeWorktreeCheckpoint`). A non-completion exit commits W's dirt to `refs/heads/moe/task/<taskId>` only: the owner guard, a temp index from the branch tip, `commit-tree`, ONE CAS `update-ref` (a lost CAS parks the bytes on a rescue ref), then a push of the task branch when `settings.checkpointPush` is on, never forced. The target and the control checkout never move. A W left dirty by a dead session gets a recovery checkpoint at the next pre-flight (`MOE_CHECKPOINT_RECOVERED`; a failure leaves the bytes in W). During a pending merge a checkpoint commits one parent and keeps W's index and `MERGE_HEAD`.
  - **Completion** (a worker exit at REVIEW/DONE; `land_worktree_completion` / `Invoke-MoeWorktreeCompletion`). L0-L2 commit W's last dirt to the task branch, then the task's net change lands on the **target** (a literal `consolidationBranch`, else `main`) as ONE squash commit:
    - L3: the `git-land-<target>` lease, taken only while `settings.qualityGate` is set (`MOE_LAND_LEASE_WAIT_SEC`, default 1800; no grant in time is `MOE_COMMIT_FAILED_LAND_LEASE`).
    - L4 (`sync_land_target` / `Sync-MoeLandTarget`): with no remote, B is the local target. In remote mode B is `refs/remotes/origin/<target>`, fetched now (3 tries `MOE_LAND_NET_BACKOFF_SEC` apart, else `MOE_LAND_FETCH_FAILED`), never the local target; a local target holding commits origin lacks is `MOE_LAND_TARGET_DIVERGED`.
    - L5: `git merge-tree --write-tree` of B and the task branch (a conflict is `MOE_COMMIT_FAILED_CONFLICT`; a merged tree equal to B's is `MOE_COMMIT_NOTHING_TO_COMMIT`), then the board guard (a merged tree that changes `.moe/` is `MOE_WORKTREE_BOARD_PATH`).
    - L6: while a `qualityGate` is set, EVERY completion gates exactly that merged tree, whatever `qualityGateScope` says, in a sparse `.moe`-free gate worktree (`run_frozen_gate worktree` / `Invoke-MoeFrozenGate -WorktreeMode`, integrity by `gate_integrity_wt` / `Test-MoeGateIntegrityWorktree`: a `.moe` there is `MOE_WORKTREE_GATE_INTEGRITY`, a nested project `MOE_WORKTREE_PROJECT_NOT_TOP`, and any failure `MOE_COMMIT_FAILED_GATE`). `MOE_DISABLE_QUALITY_GATE=1` never skips it: it fails the landing as `MOE_COMMIT_FAILED_GATE`.
    - L7-L8: C = `commit-tree M -p B` (hooks only with `settings.commitHooks`), then the receipt journal `<gitdir>/moe/receipt/<taskId>.json`, before anything is published.
    - L9-L10: with no remote, ONE CAS `update-ref` publishes. In remote mode the only publication is a non-forced `git push --porcelain origin C:refs/heads/<target>`, with no local-CAS fallback, and the local target is a mirror that only fast-forwards to origin's commit while no worktree has it checked out (else `MOE_LAND_MIRROR_SKIPPED`, a warning). `[rejected]` ends the round; `[remote rejected]` is `MOE_PUSH_FAILED`; any other answer goes to `reconcile_push` / `Resolve-MoePushOutcome`, which fetches and re-pushes the same C while origin is still at B (3 pushes), and a tip that moved on without C can never apply and ends the round. An unknown outcome is `MOE_PUSH_OUTCOME_UNKNOWN`: neither the local target nor the task branch moves, no row or finalize is sent, the journal stays (`push unknown: …`), C goes on a `push-unknown` rescue ref, and the attempt stays `finalizing` until a pre-flight replay settles it.
    - Rounds: L4-L9 repeat on a moved target, 3 rounds (2 with a `qualityGate`; `wt_land_rounds`), then `MOE_COMMIT_FAILED_REF_CONTENTION`. A target checked out in any worktree is `MOE_LAND_TARGET_CHECKED_OUT`.
    - L11-L14: `worktree_sync_branch` / `Sync-MoeTaskBranch` builds a commit with C's tree and parents T and C, and fast-forwards W onto it, hooks off, never a reset (a failure is `MOE_WORKTREE_SYNC_FAILED`, a warning: the landing stands and the next pre-flight retries), then `moe.record_commit` and `moe.finalize_attempt` `landed`, the board snapshot and the control follow; the lease is released on every path (`MOE_LAND_LEASE_RELEASE_FAILED` warns and retries once, and the lease's expiry is the backstop).
    - Retired in worktree mode: `peel_target_branch`, `ensure_safe_branch`, `moe/work-<date>` and the shared push; `MOE_PUSH_REBASE` is ignored. `moe.complete_task` expects `currentBranch` `moe/task/<taskId>` (`BRANCH-POLICY-FAIL` otherwise).
  - **The unlanded route** (`take_unlanded_route` / `Invoke-MoeUnlandedRoute`), taken only when nothing was published. `unlanded_reason` maps `MOE_COMMIT_FAILED_CONFLICT` and `MOE_WORKTREE_UNRESOLVED_CONFLICT` to `conflict`, `MOE_COMMIT_FAILED_REF_CONTENTION` and `MOE_COMMIT_FAILED_LAND_LEASE` to `contention`, `MOE_COMMIT_FAILED_GATE` and `MOE_LAND_SETTINGS_UNREADABLE` (`.moe/project.json` missing or malformed at post-flight, refused before L3) to `gate`, `MOE_LAND_TARGET_DIVERGED` to `diverged`, and `MOE_LAND_FETCH_FAILED` and `MOE_PUSH_FAILED` to `remote`. The wrapper releases the lease, puts the task-branch tip on `refs/moe/rescue/<taskId>/<utc-ts>` with the reason (`MOE_RESCUE_REF`), records the failed completion row (`pushed: false`) and calls `moe.finalize_attempt` `unlanded`. A failed rescue ref or row finalizes nothing: the bytes stay on the task branch, the attempt stays `finalizing`, and the seat stops. The daemon sets `task.landingRetry` and moves the row from REVIEW to WORKING, unassigned, or to BLOCKED for `diverged` or the 3rd consecutive unlanded landing; the next `landed` or `nothing-to-commit` finalize clears it. Any other failure (`MOE_LAND_TARGET_CHECKED_OUT`, `MOE_WORKTREE_BOARD_PATH`, a refused commit) is a plain failed row: the target never moves, the bytes stay on the task branch, and a failure inside a round also gets a `commit-failed` rescue ref.
  - **Resume** (`worktree_resume` / `Invoke-MoeWorktreeResume`). The next worker's pre-flight on a task with `landingRetry` merges the target into W with hooks off (`merge --no-commit --no-ff`; origin's target fetched now in remote mode, never a local fallback; a `MERGE_HEAD` already there is reused) and starts the prompt with `LANDING-CONFLICT: <paths>` (markers in W) or `LANDING-RETRY: <reason>` (a clean merge). The worker edits files only, re-runs the plan's verification on the merged working tree and calls `moe.complete_task`; that completion's L2 commits the merge to the task branch (`merge --quit` only after its CAS) before anything lands. At that completion, L2's marker check scans `landingRetry.paths` and the unmerged paths: a marker left is `MOE_WORKTREE_UNRESOLVED_CONFLICT`, nothing commits and the route repeats. A failed fetch or merge stops the seat with `MOE_WORKTREE_RESUME_FAILED`. Never a reset, clean, abort or automatic resolution: W keeps its bytes.
  - **Replay.** Every pre-flight replays each receipt journal (`receipt_replay` / `Invoke-MoeReceiptReplay`) and never re-lands: it never merges, gates or builds a commit. In remote mode `reconcile_push` settles the journaled C against origin. A C on the target gets its owed completion row and `landed` finalize; a C that can never apply, or one its dead lander never published while the attempt is still `finalizing`, routes that attempt unlanded (`replay_unlanded`); an unsettled push stays journaled (`MOE_PUSH_OUTCOME_UNKNOWN`), and a fresh completion of that task refuses as `MOE_COMMIT_REFUSED_UNRECONCILED_INTENT` until it settles.
  - **Control seats.** An architect or QA seat in a control checkout on `moe/control` lands nothing: it records `MOE_COMMIT_NOTHING_TO_COMMIT` and moves no branch. That working tree carries only daemon and human bytes, so the daemon's `.moe/` board diffs stay uncommitted there.
  - **Board history** (`board_snapshot` / `Invoke-MoeBoardSnapshot`, while `autoCommit` and `commitBoardState` are on). No worktree landing carries a `.moe/` path. After a settled worker completion, and at a QA seat's exit, the wrapper commits `.moe/project.json`, `.moe/tasks/*.json` and `.moe/epics/*.json` to `refs/moe/board` (a private index and a CAS, 3 tries; never a branch, HEAD, the real index or `.moe/`) and pushes that ref plainly, never forced. `MOE_BOARD_FILE_KEPT` (a file not read cleanly as JSON keeps its previous snapshot), `MOE_BOARD_SNAPSHOT_SKIPPED` and `MOE_BOARD_UNPUSHED` are warnings and never change the landing's outcome.
  - **Control follow** (L13, `follow_control_checkout` / `Invoke-MoeControlFollow`). A control checkout on `moe/control` fast-forwards to the target (`merge --ff-only`, hooks off), so the wrapper on disk is always committed bytes: at every loop top before the hot-reload hash check (any seat), after a worker's settled completion, and in a QA pre-flight (`qa_control_preflight`, which first syncs origin's target in remote mode). QA reviews landed bytes only: `qa_landed_gate` / `Assert-MoeQaLandedCommit` stops the QA seat with `MOE_CONTROL_CHECKOUT_BEHIND` and one `moe.report_blocked` unless the task's recorded completion is a commit in the control HEAD, and then names `git diff <sha>^ <sha>` in the prompt.

The orphan sweep (`worktree_orphan_sweep` / `Invoke-MoeWorktreeSweep`) runs at a loop top in a control checkout on `moe/control`, at most every `MOE_WORKTREE_SWEEP_INTERVAL_SEC` (default 3600; 0 means every loop top) under one sweep lock (a held lock skips the pass), with at most 5 removals a pass. It skips a task with an open attempt or one the daemon reports neither DONE nor ARCHIVED (an unknown task is removable), and first puts W's non-DENY dirt and an unlanded branch tip on `worktree-orphan` rescue refs, refusing the removal when a rescue ref does not hold every byte. An unregistered `.worktrees/task-*` directory is named (`MOE_WORKTREE_UNREGISTERED`, one #general alert per path a day) and left on disk. Moe touches only `.worktrees/task-*`: a human's or a skill's other `.worktrees/` checkouts stay theirs.

- **Heartbeat sidecar** (`moe-agent.{sh,ps1}`): the wrapper blocks synchronously on the CLI subprocess for its whole runtime with zero interleaved activity, and `moe-proxy` opens a fresh connection per RPC call rather than holding one for the CLI's lifetime — so the daemon's only liveness signal is "did this worker call a moe.* tool recently." A long silent local step (a build, a full test run) can outlast `reviewStaleTimeoutMs` even while the CLI is still very much alive and about to call `qa_approve`/`qa_reject`, which would otherwise let the REVIEW self-heal above steal the task out from under a live session. The wrapper runs a background sidecar (PowerShell `Start-Job` / bash backgrounded subshell) alongside the blocking CLI call that pings the no-op `moe.heartbeat` tool on a timer (`MOE_HEARTBEAT_INTERVAL_SEC`, default 60s) to keep `lastActivityAt` fresh, bounded by `MOE_HEARTBEAT_MAX_DURATION_SEC` (default 2h) so a truly-hung CLI still eventually goes stale — this extends the self-heal's patience window, it does not defeat it. Stopped via `Stop-HeartbeatSidecar`/`stop_heartbeat_sidecar` after each CLI invocation and from the Ctrl+C/exit-handler paths. Cleanup waits are bounded: Bash checks its own running/stopped job table, gives the tracked helper 2s after TERM then 2s after KILL, and never waits unconditionally on a live helper. PowerShell runs the exact tracked job's synchronous `StopJob` in one retained asynchronous runspace and waits at most 2s per call; it never force-removes a nonterminal job. A timeout warns `MOE_HEARTBEAT_STOP_TIMEOUT`, preserves the job/PID (and pending stop operation), and refuses to start a duplicate sidecar; post-flight can proceed. No peer process/group is signalled and no task or lease is released by this cleanup. Bash escalation is explicitly logged as `MOE_HEARTBEAT_STOP_ESCALATED`. A `Start-Job` child is a real separate process, so an unresolved timeout is not proof it has exited. On a `reattachRequired` answer (`attempt-reconciling`, after a daemon restart) the sidecar reattaches the attempt the answer names, reading its `taskId`/`generation` from `.moe/attempts/<id>.json` (contract: `moe.heartbeat` in `docs/MCP_SERVER.md`). Architect/QA/governor seats also export the runner identity as `MOE_RUNNER_PROCESS_STARTED_AT`/`MOE_RUNNER_HOST`, which `moe-proxy` stamps onto in-session `claim_next_task` calls so those attempts reattach too; a worker seat unsets both (its wrapper finalizes only its own claim's attempt). Opt out via `MOE_DISABLE_HEARTBEAT=1`.
- **Hot reload**: at the loop top (after the poll sleep, before dispatch), a changed wrapper sha256 reloads once per hash (sh `exec`, ps1 in-process supervisor), deregistering with reason `wrapper_restart`. The daemon then holds the seat's active tasks for the relaunch instead of releasing them (task-4ddbfb31). The hold lasts `settings.reloadHoldMs`, default 2 min; `0` releases at once, as before. No peer can claim the held tasks in the gap. The reloaded wrapper's first `claim_next_task` ends the hold and answers `alreadyAssigned`, so the seat resumes its own task with a fresh resume counter. If the relaunch never claims, the 60 s worker sweep releases the tasks once the window is over. Contract: **A hot reload holds its tasks** under `moe.deregister_worker` in `docs/MCP_SERVER.md`. Only **committed bytes** reload: the file must be tracked in the wrapper's own checkout, never the project's, and match HEAD (`git ls-files --error-unmatch`, then `git diff --quiet HEAD`). A reload never loads the shared path: it copies the bytes into a private `moe-wrapper-pin.*` temp folder, requires the copy's blob (`git hash-object --path=<leaf>`) to equal `HEAD:<leaf>`, parses the copy and runs it (sh: `exec "$BASH" <copy>` with `MOE_WRAPPER_SOURCE` naming the checkout; ps1: the supervisor runs `$global:MoeWrapperReloadPin` and helpers resolve beside `$global:MoeWrapperSourcePath`), so a write after the check stays unloaded until it is committed (task-69c02444). A failed copy defers (`(private copy failed)`); committed bytes that do not name the hand-over reload from the checkout path (revert-safe); a ps1 seat launched before this change keeps its old supervisor until relaunched. The copy deletes itself once loaded (ps1: the supervisor also drops it after the pass, as a fallback). Uncommitted edits defer with one `[INFO] MOE_WRAPPER_RELOAD_DEFERRED: wrapper has uncommitted edits` line per hash; the seat keeps serving current bytes and reloads once they are committed (a checkpoint/wip commit counts). A failed check (no git, not a work tree — including a plugin-bundled copy — unborn HEAD, unreadable index) also defers, with `[WARN] MOE_WRAPPER_RELOAD_DEFERRED: cannot confirm the wrapper bytes are committed (...)`, never ending or deregistering the seat; relaunch such a seat by hand to load new bytes. Committed bytes failing `bash -n` or ParseFile are refused once per hash (`MOE_WRAPPER_RELOAD_REFUSED`). The sh main loop and post-loop tail are parsed as ONE group (`{` before the loop, `exit` and `}` after the tail): once the loop starts, bash never reads moe-agent.sh again. Before task-f31d415d, an in-place rewrite (same inode: editor save, apply_patch) made a seat whose loop ended read new tail bytes from its stale saved offset. Wrapper saves must not rely on in-place rewrites being safe for older seats: earlier bytes still read the tail from disk, and launch code above the loop is still parsed incrementally. Write the whole file elsewhere on the same filesystem, `bash -n` it, then one `mv -f` over the target; running seats keep the old inode. PowerShell parses the whole file, so ps1 needs no group. Tests: the seven `[hot reload*]` arms of `postflight.{sh,ps1}` (`[hot reload race]` and `[hot reload hold]` included) and the sh-only `[stale offset]` arm of `postflight.sh`.
- **Execution identity** (CQ-F09 to CQ-F12a; `moe-agent.{sh,ps1}`; the proxy side, with its validity rules and refusals, is in `packages/moe-proxy/README.md`): every iteration exports `MOE_SESSION_ID` = `<workerId>@<preflight-iso>`, the same id `moe.record_commit` takes as `sessionId`. The pre-flight `get_context` is the one served read: its args are `{taskId}`, plus `sessionId` when `MOE_SESSION_ID` is set. After the pre-flight claim (a fresh claim, or the held task of a resume), `pin_attempt_identity` (sh) / `Set-MoeAttemptIdentity` (ps1) export `MOE_ATTEMPT_ID` + `MOE_ATTEMPT_GENERATION` only once the claim's attempt record verifies against the store. The pair is both-or-neither: any failure leaves both blank with `[WARN] Missing/stale attempt identity; candidate completion will fail closed.`, a resume refreshes it from the store, and the loop top resets it so no CLI inherits a previous task's attempt (a hot reload keeps env). Post-flight and adoption `get_context` reads are unserved: `moe_rpc_unserved` (sh) / `Invoke-MoeRpcUnserved` (ps1) blank `MOE_SESSION_ID` for that one call, so the proxy stamps no `sessionId` and they mint no receipt. `moe-proxy` stamps the identity onto `get_context`, `start_step`, `complete_step`, `complete_task`, `qa_approve` and `qa_reject` (CQ-V06a) and refuses a caller-substituted or malformed one, so the seat's CLI can never present its own.
