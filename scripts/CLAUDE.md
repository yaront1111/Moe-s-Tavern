# scripts/CLAUDE.md

Agent launcher detail (`scripts/moe-agent.{sh,ps1}`, `moe-team.{sh,ps1}`). Project overview, build and test commands: root `CLAUDE.md`. Keep `.sh` and `.ps1` in string parity (`bash scripts/tests/parity-check.sh`).

## Per-CLI launch

`grok` (xAI Grok Build) follows the same role-based polarity: headless is `--prompt-file <temp file> --yolo --cwd <project> --no-auto-update --output-format plain` (the per-iteration prompt travels through a temp file — grok reads no stdin and has no `--prompt` flag), interactive passes a short pointer prompt positionally, and `-GrokExec`/`--grok-exec` forces headless; auth is `XAI_API_KEY` or a cached `grok login` (`~/.grok/auth.json`; a non-fatal `[WARN]` when both are missing). `codex` runs the interactive TUI for every role by default (a TUI seat lands its commits only when the operator closes the TUI, so opt a seat into one-shot headless with `-CodexExec`/`--codex-exec` when per-task landing matters); headless is `codex -c <per-seat overrides> -c approvals_reviewer=user exec -C <project> --sandbox <MOE_CODEX_SANDBOX, default danger-full-access>` — **never `--full-auto`**: codex-cli 0.147+ rejects it with exit 2 before any work and the wrapper relaunch-loops (the standalone codex installer auto-updates, so any seat can hit it); `exec` already implies `approval_policy=never` and the reviewer pin keeps that even under an operator `approvals_reviewer = "auto_review"`, `MOE_CODEX_SANDBOX=inherit` omits the flag (read-only when no config sets `sandbox_mode`). The default is full access, not `workspace-write`, because codex 0.148+ refuses every un-annotated MCP tool (all of `moe.*`) under `never` + any sandbox (`MCP tool call requires approval, but approval policy is never`) and the Windows unelevated sandbox (`[windows] sandbox = "unelevated"`) cannot spawn a Store-installed pwsh (`CreateProcessAsUserW failed: 5`; `codex sandbox -- <cmd>` reproduces it offline) — the config writer also pins `default_tools_approval_mode = "approve"` on the moe/serena servers so an explicit `workspace-write` keeps MCP working (without `[windows] sandbox` at all, `workspace-write` silently runs read-only on Windows). `parity-check.{sh,ps1}` fail on any `--full-auto` reintroduction. Before the first headless launch the wrapper probes the real argv plus `--help` once per process; a codex that rejects a flag stops the seat with `MOE_CLI_ARGV_REJECTED` + a `#general` escalation instead of relaunch-looping (`MOE_DISABLE_ARGV_PROBE=1` skips it). Model defaults: `claude-opus-5-5` for every role (launched with `--effort max`; a claimed task's `launch` hint from `claim_next_task` sets that session's effort, and its model unless the operator pinned one), honored only by the `claude` CLI; codex instead gets `model_reasoning_effort = "xhigh"` written into its config.toml (override via `MOE_CODEX_REASONING_EFFORT`), and a claimed task's `launch.codex` hint adds per-launch `-m <model>` and `-c model_reasoning_effort=<effort>` on both the TUI and `exec` paths (the argv probe included) — the operator pin wins (`--model`/`settings.models.{role}` for the model, `MOE_CODEX_REASONING_EFFORT` for the effort); grok gets `-m` only when a model is explicit (`-Model`/`--model`, `settings.models.{role}`, else `MOE_GROK_MODEL` — never the claude fallback) and `--effort` only from `MOE_GROK_EFFORT`; override the claude model via `-Model`/`--model` or `settings.models.{role}`.

## Wrapper behaviour

- **Land on every exit** (`scripts/moe-agent.{ps1,sh}` post-flight — the wrappers are the Git-write actors; the daemon is state-only: it never writes git state, lands, pushes or runs the gate, and its Git reads are the status fingerprint for handoff notes plus bounded cached-ref affected-path validation (no fetch or checkout)). With `settings.autoCommit` on (default) every session exit that holds a task lands its bytes. A **worker** exit at `REVIEW`/`DONE` makes a *completion* commit (`feat|fix(task-<id>): <title>`) and pushes; any other exit (WORKING/BLOCKED/PLANNING/AWAITING_APPROVAL, or a failed status lookup → `status=UNKNOWN`) for worker/architect/qa makes a *checkpoint* commit (`wip(task-<id>): … [status=<S> role=<r> cli-exit=<N>]`; pushed per `settings.checkpointPush`, default on; off via `settings.checkpointCommits=false` or `MOE_DISABLE_CHECKPOINT=1`). Attribution is per task and pathspec-only (`:(literal)`; never `git add -A`/`-u`, never a bare `git commit` against the shared index, no whole-tree fallback): a per-task baseline snapshot (`<gitdir>/moe/baseline/<taskId>.tsv`, taken at pre-flight, pruned after each landing, kept until DONE/ARCHIVED) plus `moe.get_commit_scope` tier every dirty path — **ASSERTED** (completed-step `modifiedFiles`, `declare_files`, prior commits — `declare_files` paths committed regardless of baseline, the rest only when this task produced the dirty bytes: tool-written, changed since the landing session's pre-flight snapshot (`P` rows; a crash recovery uses the dead session's), or carried as its own from its previous session (`C` rows) — else `MOE_ATTR_ASSERTED_FOREIGN`), **PLANNED** (plan-declared; only if changed since baseline), **TOOL** (supported Claude editing calls with matching successful `tool_result` events; declarations and completed-step reports remain ASSERTED), **MEASURED** (undeclared + changed; committed only when `attribution.undeclared` allows — default `'solo'` = no other live worker — else reported as `MOE_ATTRIBUTION_UNRESOLVED`), **PEER** (`MOE_ATTR_PEER_DECLARED` skip), **PREEXISTING** (`MOE_ATTR_PREEXISTING` skip — dirty before the task and untouched is never committed), **DENY** (`MOE_ATTR_EXCLUDED`: `.moe/**` except BOARD, `.mcp.json`, `.codex/**`, `.gemini/**`, `.grok/**`, `.claude/agents/**`, `.worktrees/**`, `attribution.exclude`), **BOARD** (own `.moe/tasks/<id>.json`). Landing = temp index + `commit-tree` + `update-ref` CAS (3 attempts; `MOE_COMMIT_FAILED_REF_CONTENTION` after), so peers' staged entries survive and git hooks do **not** run unless `settings.commitHooks=true` (then completion hooks run with a private index and detached HEAD; only the validated tree/parent reaches the branch CAS, and hook failure, tree mutation, signing/author configuration mismatch, or unborn HEAD refuses landing with rescue; checkpoints stay plumbing). Gate-failed (`settings.qualityGate`, epic-final by default, `MOE_DISABLE_QUALITY_GATE=1` skips), peel-failed, commit-failed, ref-contention and Ctrl+C teardown never touch the branch: the bytes go to a **rescue ref** `refs/moe/rescue/<taskId>/<utc-ts>` (`MOE_RESCUE_REF` chat line; never pushed), the baseline is kept, and the next pre-flight of that task lands it as a checkpoint (`MOE_CHECKPOINT_RECOVERED`). Refusal codes `MOE_COMMIT_REFUSED_NO_OWNED_PATHS` / `MOE_COMMIT_REFUSED_OWNED_PATH_MISSING` keep their meaning; `MOE_COMMIT_NOTHING_TO_COMMIT` is the idempotent no-op. Every outcome is reported via `moe.record_commit` into `task.commits`. Branch safety: never commit on `main`/`master`/detached — peel onto literal `settings.consolidationBranch` else the shared `moe/work-<YYYY-MM-DD>` (not branch-per-task; existing non-default branches are reused).
- **Heartbeat sidecar** (`moe-agent.{sh,ps1}`): the wrapper blocks synchronously on the CLI subprocess for its whole runtime with zero interleaved activity, and `moe-proxy` opens a fresh connection per RPC call rather than holding one for the CLI's lifetime — so the daemon's only liveness signal is "did this worker call a moe.* tool recently." A long silent local step (a build, a full test run) can outlast `reviewStaleTimeoutMs` even while the CLI is still very much alive and about to call `qa_approve`/`qa_reject`, which would otherwise let the REVIEW self-heal above steal the task out from under a live session. The wrapper runs a background sidecar (PowerShell `Start-Job` / bash backgrounded subshell) alongside the blocking CLI call that pings the no-op `moe.heartbeat` tool on a timer (`MOE_HEARTBEAT_INTERVAL_SEC`, default 60s) to keep `lastActivityAt` fresh, bounded by `MOE_HEARTBEAT_MAX_DURATION_SEC` (default 2h) so a truly-hung CLI still eventually goes stale — this extends the self-heal's patience window, it does not defeat it. Stopped via `Stop-HeartbeatSidecar`/`stop_heartbeat_sidecar` after each CLI invocation and from the Ctrl+C/exit-handler paths. Cleanup waits are bounded: Bash checks its own running/stopped job table, gives the tracked helper 2s after TERM then 2s after KILL, and never waits unconditionally on a live helper. PowerShell runs the exact tracked job's synchronous `StopJob` in one retained asynchronous runspace and waits at most 2s per call; it never force-removes a nonterminal job. A timeout warns `MOE_HEARTBEAT_STOP_TIMEOUT`, preserves the job/PID (and pending stop operation), and refuses to start a duplicate sidecar; post-flight can proceed. No peer process/group is signalled and no task or lease is released by this cleanup. Bash escalation is explicitly logged as `MOE_HEARTBEAT_STOP_ESCALATED`. A `Start-Job` child is a real separate process, so an unresolved timeout is not proof it has exited. Opt out via `MOE_DISABLE_HEARTBEAT=1`.
- **Compaction window + keeper mod** (claude launches only): the wrapper sets `CLAUDE_CODE_AUTO_COMPACT_WINDOW` per role (worker 300000, qa 500000, architect/governor 600000) and records its own value in `MOE_COMPACT_WINDOW_DEFAULT`, so a hot reload (sh `exec`, ps1 in-process supervisor — both keep the env) re-derives it while an unmarked operator value wins; a bare `300000` counts as the pre-2026-10-09 wrapper default. It also appends `scripts/mods/moe-compaction-keeper` to `CLAUDE_CODE_PLUGIN_DIRS` (path-list, `:`/`;`; opt out `MOE_DISABLE_COMPACTION_KEEPER=1`): a Claude Code mod whose `session.compact` hook, for a seat's main transcript only (`MOE_WORKER_ID` set, no `agentId`), adds Moe keep-instructions to the summarizer and inserts a task snapshot (status, steps, DoD, last QA rejection) read from `.moe/workers/<id>.json` + `.moe/tasks/<taskId>.json` after the summary; any failure falls through to plain compaction. Test with `claude plugin test scripts/mods/moe-compaction-keeper`; the launcher blocks are covered by `scripts/tests/prompt-cache-launcher.test.mjs`. Both IDE bundles ship `scripts/mods/**` minus `*.test.ts` and the engine-written `.claude-plugin/types/`.
- **MCP servers for spawned agents** are built entirely by `scripts/moe-agent.{ps1,sh}` (the daemon schema has no MCP field), per CLI: `claude` gets a temp `--mcp-config` (PowerShell) or `~/.config/claude/mcp_servers.json` merge + `$PROJECT/.mcp.json` (bash); `codex` gets `.codex/config.toml` (`[mcp_servers.*]`); `gemini` gets `.gemini/settings.json` (`mcpServers`); `grok` gets `.grok/config.toml` (the same `[mcp_servers.*]` TOML as codex but **no top-level keys** — a grok project config may only carry `[mcp_servers.*]`/`[plugins]`/`[permission]`/`[mcp]` — with `MOE_WORKER_ID = "${MOE_WORKER_ID:-}"` written literally because grok expands `${VAR:-default}` per process; the wrapper also sets `GROK_CLAUDE_MCPS_ENABLED=0`/`GROK_CURSOR_MCPS_ENABLED=0` so grok stops auto-merging `~/.claude.json` and `.cursor/mcp.json` on top of it — a project `.mcp.json` can still be merged, `grok inspect` shows each server's origin — plus `GROK_DISABLE_AUTOUPDATER=1`). Two more grok-only wrapper steps, both measured necessary 2026-09-05 (grok 1.0.13): the `moe` env table also pins `MOE_TOOL_NAME_STYLE = "underscore"` because grok silently drops any MCP tool whose name contains a dot (the daemon's `moe.<name>` — the server showed as connected with 0 tools, then "failed to connect"), so the proxy exposes `moe_<name>` in `tools/list` and maps the alias back on `tools/call`; and the wrapper pre-trusts the project in `~/.grok/trusted_folders.toml` (`Grok folder trust granted: <path>`), because grok refuses a project's `.grok/config.toml` MCP servers in an untrusted folder and a headless worker never sees the TUI's trust prompt. Grok reaches MCP tools only through its `search_tool`/`use_tool` dispatchers under qualified names (`moe__moe_<name>`, `serena__<tool>`); the wrapper's prompt says so. The grok `moe` entry also carries `tool_timeout_sec = 120` (`MOE_GROK_MCP_TOOL_TIMEOUT_SEC`) with a 720s `tool_timeouts` override for the three blocking long-polls — grok's 6000s default let one lost (undecodable) response park a call for minutes. **All four CLIs** inject the `moe` proxy server **and** a **Serena** server (LSP symbol navigation/editing + project memory) pinned to the project (headless — no dashboard/GUI), giving every role exact cross-file code intelligence and shared memory instead of whole-file reads. The codex and grok `moe` entries get `startup_timeout_sec` 120 (override `MOE_CODEX_MCP_STARTUP_TIMEOUT_SEC` / `MOE_GROK_MCP_STARTUP_TIMEOUT_SEC`; codex's 30s default loses the race against a supervised daemon restart), and because both TOML writers run **before** daemon host probing, WSL runs upsert the discovered `MOE_DAEMON_HOST` into `[mcp_servers.moe.env]` after discovery — so the written config stays self-contained even if the CLI doesn't forward the wrapper's environment to spawned MCP servers. Serena's project root is `serenaProject` in `<project>/.moe-agent.json`, else `MOE_SERENA_PROJECT`, else the Moe project root (the override exists for multi-repo workspace roots); its `--context` is `claude-code`/`codex`/`agent`/`agent` for claude/codex/gemini/grok. Serena is resolved from `MOE_SERENA_PATH` or `%USERPROFILE%\.local\bin\serena.exe`/`~/.local/bin/serena` and **no-ops if not installed** (`uv tool install -p 3.13 serena-agent`); the codex/gemini/grok writers are idempotent (re-runs don't duplicate the `serena` entry). To add more MCP servers for agents, extend these two scripts — there is no other hook.
