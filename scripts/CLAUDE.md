# scripts/CLAUDE.md

Agent launcher detail (`scripts/moe-agent.{sh,ps1}`, `moe-team.{sh,ps1}`). Project overview, build and test commands: root `CLAUDE.md`. Keep `.sh` and `.ps1` in string parity (`bash scripts/tests/parity-check.sh`). Keep `moe-agent.ps1` saved as UTF-8 with a BOM: Windows PowerShell 5.1, which the JetBrains plugin uses for native Windows seats, reads a BOM-less script as ANSI and cannot parse its non-ASCII text (the parity check enforces it).

## Per-CLI launch

`grok` (xAI Grok Build) follows the same role-based polarity: headless is `--prompt-file <temp file> --yolo --cwd <project> --no-auto-update --output-format plain` (the per-iteration prompt travels through a temp file — grok reads no stdin and has no `--prompt` flag), interactive passes a short pointer prompt positionally, and `-GrokExec`/`--grok-exec` forces headless; auth is `XAI_API_KEY` or a cached `grok login` (`~/.grok/auth.json`; a non-fatal `[WARN]` when both are missing). `codex` runs the interactive TUI for every role by default (a TUI seat lands its commits only when the operator closes the TUI, so opt a seat into one-shot headless with `-CodexExec`/`--codex-exec` when per-task landing matters); headless is `codex -c <per-seat overrides> -c approvals_reviewer=user exec -C <project> --sandbox <MOE_CODEX_SANDBOX, default danger-full-access>` — **never `--full-auto`**: codex-cli 0.147+ rejects it with exit 2 before any work and the wrapper relaunch-loops (the standalone codex installer auto-updates, so any seat can hit it); `exec` already implies `approval_policy=never` and the reviewer pin keeps that even under an operator `approvals_reviewer = "auto_review"`, `MOE_CODEX_SANDBOX=inherit` omits the flag (read-only when no config sets `sandbox_mode`). The default is full access, not `workspace-write`, because codex 0.148+ refuses every un-annotated MCP tool (all of `moe.*`) under `never` + any sandbox (`MCP tool call requires approval, but approval policy is never`) and the Windows unelevated sandbox (`[windows] sandbox = "unelevated"`) cannot spawn a Store-installed pwsh (`CreateProcessAsUserW failed: 5`; `codex sandbox -- <cmd>` reproduces it offline) — the config writer also pins `default_tools_approval_mode = "approve"` on the moe/serena servers so an explicit `workspace-write` keeps MCP working (without `[windows] sandbox` at all, `workspace-write` silently runs read-only on Windows). `parity-check.{sh,ps1}` fail on any `--full-auto` reintroduction. Before the first headless launch the wrapper probes the real argv plus `--help` once per process; a codex that rejects a flag stops the seat with `MOE_CLI_ARGV_REJECTED` + a `#general` escalation instead of relaunch-looping (`MOE_DISABLE_ARGV_PROBE=1` skips it). Model defaults: `claude-opus-5-5` for every role (launched with `--effort max`; a claimed task's `launch` hint from `claim_next_task` sets that session's effort, and its model unless the operator pinned one), honored only by the `claude` CLI; codex instead gets `model_reasoning_effort = "xhigh"` written into its config.toml (override via `MOE_CODEX_REASONING_EFFORT`), and a claimed task's `launch.codex` hint adds per-launch `-m <model>` and `-c model_reasoning_effort=<effort>` on both the TUI and `exec` paths (the argv probe included) — the operator pin wins (`--model`/`settings.models.{role}` for the model, `MOE_CODEX_REASONING_EFFORT` for the effort); grok gets `-m` only when a model is explicit (`-Model`/`--model`, `settings.models.{role}`, else `MOE_GROK_MODEL` — never the claude fallback) and `--effort` only from `MOE_GROK_EFFORT`; override the claude model via `-Model`/`--model` or `settings.models.{role}`.

## Wrapper behaviour

- **Land on every exit** (`scripts/moe-agent.{ps1,sh}` post-flight — the wrappers are the Git-write actors; the daemon is state-only: it never writes git state, lands, pushes or runs the gate, and its Git reads are the status fingerprint for handoff notes plus bounded cached-ref affected-path validation (no fetch or checkout)). With `settings.autoCommit` on (default) every session exit that holds a task lands its bytes. A **worker** exit at `REVIEW`/`DONE` makes a *completion* commit (`feat|fix(task-<id>): <title>`) and pushes; any other exit (WORKING/BLOCKED/PLANNING/AWAITING_APPROVAL, or a failed status lookup → `status=UNKNOWN`) for worker/architect/qa makes a *checkpoint* commit (`wip(task-<id>): … [status=<S> role=<r> cli-exit=<N>]`; pushed per `settings.checkpointPush`, default on; off via `settings.checkpointCommits=false` or `MOE_DISABLE_CHECKPOINT=1`). Attribution is per task and pathspec-only (`:(literal)`; never `git add -A`/`-u`, never a bare `git commit` against the shared index, no whole-tree fallback): a per-task baseline snapshot (`<gitdir>/moe/baseline/<taskId>.tsv`, taken at pre-flight, pruned after each landing, kept until DONE/ARCHIVED) plus `moe.get_commit_scope` tier every dirty path — **ASSERTED** (completed-step `modifiedFiles`, `declare_files`, prior commits — `declare_files` paths committed regardless of baseline unless DENY or CONTESTED holds them, the rest only when this task produced the dirty bytes: tool-written, changed since the landing session's pre-flight snapshot (`P` rows; a crash recovery uses the dead session's), or carried as its own from its previous session (`C` rows) — else `MOE_ATTR_ASSERTED_FOREIGN`), **PLANNED** (plan-declared; only if changed since baseline), **TOOL** (supported Claude editing calls with matching successful `tool_result` events, and a `codex exec` seat's `--json` events: each path of a completed `file_change` and a successful Serena editing `mcp_tool_call` under the same per-tool rules, harvested by `scripts/prompt-cache-witness.mjs`; a Codex TUI, Gemini, Grok or interactive Claude session leaves none; declarations and completed-step reports remain ASSERTED), **MEASURED** (undeclared + changed; committed only when `attribution.undeclared` allows — default `'solo'` = no other live worker — else reported as `MOE_ATTRIBUTION_UNRESOLVED`), **PEER** (`MOE_ATTR_PEER_DECLARED` skip), **CONTESTED** (an own path another nonterminal task also declares, per `attribution.contested`: the default `skip-untouched` first holds it as `MOE_ATTR_CONTESTED_EDITING(task-<peer>)` while a contesting task is mid-step on it (an IN_PROGRESS plan step naming the path with an active session, `get_commit_scope` `editingTaskIds`; the disk fallback counts any IN_PROGRESS step), even when this session's editing tool wrote it, then lands it only when this session's supported editing tool wrote it, or when it was clean at this session's pre-flight and every contesting task is idle, else holds it as `MOE_ATTR_CONTESTED_UNTOUCHED(task-<peer>)`; `skip` holds it as `MOE_ATTR_CONTESTED` whatever the tools did; `commit` lands it; an older daemon without `editingTaskIds` lands as before; only a landed one carries a trailer, one per path naming every contesting task (`Moe-Contested: <path> (task-<a>, task-<b>)`), and `moe.record_commit`'s `contested` list has one row per (task, path). A `declare_files` entry never releases a hold, idle peer or not: a path dirty at pre-flight can carry the peer's hunks. The session-ended line names each held path `held=<path>(task-<peer>)` (five, then `+N more`) followed by one `MOE_CONTESTED_HELD remedy:` (a clause per held kind), and `moe.record_commit` alerts `#governors` with the same remedy. Under `skip-untouched`, verify the bytes are this task's and coordinate any live peer, then either the assignee's own session edits the path with a wrapper-observed editing tool (a shell write leaves no witness) or the stale peer task is legitimately completed or archived; an EDITING hold first waits for the peer's step to finish (then re-edit), or the peer's own landing carries the bytes; under `skip` only the peer route works. Never weaken the policy, auto-archive a peer or hand-land the path as the fix), **PREEXISTING** (`MOE_ATTR_PREEXISTING` skip — dirty before the task and untouched is never committed), **DENY** (`MOE_ATTR_EXCLUDED`: `.moe/**` except BOARD, `.mcp.json`, `.codex/**`, `.gemini/**`, `.grok/**`, `.claude/agents/**`, `.worktrees/**`, `attribution.exclude`), **BOARD** (own `.moe/tasks/<id>.json`). Landing = temp index + `commit-tree` + `update-ref` CAS (3 attempts; `MOE_COMMIT_FAILED_REF_CONTENTION` after), so peers' staged entries survive and git hooks do **not** run unless `settings.commitHooks=true` (then completion hooks run with a private index and detached HEAD; only the validated tree/parent reaches the branch CAS, and hook failure, tree mutation, signing/author configuration mismatch, or unborn HEAD refuses landing with rescue; checkpoints stay plumbing). Gate-failed (`settings.qualityGate`, epic-final by default, `MOE_DISABLE_QUALITY_GATE=1` skips), peel-failed, commit-failed, ref-contention and Ctrl+C teardown never touch the branch: the bytes go to a **rescue ref** `refs/moe/rescue/<taskId>/<utc-ts>` (`MOE_RESCUE_REF` chat line; never pushed), the baseline is kept, and the next pre-flight of that task lands it as a checkpoint (`MOE_CHECKPOINT_RECOVERED`) — except under the strong profile (verified-local, read from the task's attempt record or receipt journal, never the environment), where every checkpoint landing, recoveries included, is refused (`MOE_COMMIT_REFUSED_STRONG_CHECKPOINT`: no commit, ref, rescue ref or index entry is written) and the bytes and baseline stay for the verified completion. Refusal codes `MOE_COMMIT_REFUSED_NO_OWNED_PATHS` / `MOE_COMMIT_REFUSED_OWNED_PATH_MISSING` keep their meaning; `MOE_COMMIT_NOTHING_TO_COMMIT` is the idempotent no-op. Under the strong profile a completion moves the target only through its receipt journal `<gitdir>/moe/receipt/<taskId>.json`, made durable before `update-ref` (CQ-V07/V08): no frozen candidate of the landed tree, or no pinned attempt and plan revision, refuses it as `MOE_COMMIT_REFUSED_INTENT_INCOMPLETE`, a journal that cannot be made durable as `MOE_COMMIT_REFUSED_INTENT_UNWRITABLE`, and an earlier landing's journal still on disk as `MOE_COMMIT_REFUSED_UNRECONCILED_INTENT` (none writes a ref, rescue ref or push; the bytes and baseline stay); the attempt stays `finalizing` until the receipt is recorded (`MOE_FINALIZE_DEFERRED_RECEIPT`, settled by a pre-flight replay); and a landing whose commit on the target does not carry the verified tree (a rebase) is never adopted as proof (`MOE_DELIVERY_PROOF_NOT_TRANSFERRED`; `MOE_PUSH_REBASE` is ignored). **Owner guard** (`landing_owner_guard` / `Get-MoeOwnerGuard`; runs first in the post-flight landing, the pre-flight recovery — on a fresh scope — and the teardown rescue): a session that is not the task's assignee (an architect whose planned task a worker took, a QA seat whose row moved on) lands none of the task's bytes, source or BOARD, while the owner is protected — `get_commit_scope.assigneeProtected: true`, a registered non-DEAD seat or one holding an open attempt (`assigneeAlive` is display presence, never proof of death) — or while another seat's attempt on the task is still `finalizing` (`complete_task` clears the assignee before that seat's wrapper lands): `MOE_COMMIT_REFUSED_ACTIVE_ASSIGNEE`. Only a JSON `false` clears a foreign owner; an absent or non-boolean answer (an older daemon), a missing or malformed owner, a failed check or the disk fallback refuses as `MOE_COMMIT_REFUSED_OWNER_UNKNOWN`. A refusal moves nothing (no commit, ref, rescue or push; tree, shared index and baseline untouched), records `outcome: refused` with its code and no path fields, and ends the session line `commit=none … outcome=refused code=<code>`; the owner's own landing then commits those bytes. The assignee itself, an unassigned task, and a dead or absent owner (`assigneeProtected: false`) with nothing finalizing land as before, so orphan recovery is unchanged. The scope read and the branch CAS are two steps, not one atomic check. Every outcome is reported via `moe.record_commit` into `task.commits`. Branch safety: never commit on `main`/`master`/detached — peel onto literal `settings.consolidationBranch` else the shared `moe/work-<YYYY-MM-DD>` (not branch-per-task; existing non-default branches are reused).
  **Agent Git-write guard:** every CLI launch inherits a temporary, process-only `includeIf.gitdir`/`core.hooksPath` overlay for the exact control checkout. Ordinary agent/subagent `git commit` and `git push` fail with `MOE_AGENT_GIT_REFUSED: the wrapper lands the work`, including after a failed scratch `cd`. Separate repositories and linked worktrees keep their own hooks. No installed hook or persistent Git configuration is changed: other hooks delegate to their original absolute files. The wrapper/sidecars never inherit this overlay; completion/checkpoint landing and `settings.commitHooks` semantics are unchanged. Setup/identity/configuration/permission validation failure stops launch with `MOE_AGENT_GIT_GUARD_FAILED`; non-Git projects launch without claiming protection. This is an accidental-write guard, **not a malicious-agent sandbox**: `--no-verify`, explicit `core.hooksPath`, or stripping inherited Git configuration can bypass it. A human-only, one-command override (with restoration) is documented in [Troubleshooting](../docs/TROUBLESHOOTING.md#agent-git-write-refusal); agents must not use that override to repair landing. Use `cd /absolute/scratch && git ...` or `git -C /absolute/scratch ...`, never continue Git commands after a failed `cd`.
- **Heartbeat sidecar** (`moe-agent.{sh,ps1}`): the wrapper blocks synchronously on the CLI subprocess for its whole runtime with zero interleaved activity, and `moe-proxy` opens a fresh connection per RPC call rather than holding one for the CLI's lifetime — so the daemon's only liveness signal is "did this worker call a moe.* tool recently." A long silent local step (a build, a full test run) can outlast `reviewStaleTimeoutMs` even while the CLI is still very much alive and about to call `qa_approve`/`qa_reject`, which would otherwise let the REVIEW self-heal above steal the task out from under a live session. The wrapper runs a background sidecar (PowerShell `Start-Job` / bash backgrounded subshell) alongside the blocking CLI call that pings the no-op `moe.heartbeat` tool on a timer (`MOE_HEARTBEAT_INTERVAL_SEC`, default 60s) to keep `lastActivityAt` fresh, bounded by `MOE_HEARTBEAT_MAX_DURATION_SEC` (default 2h) so a truly-hung CLI still eventually goes stale — this extends the self-heal's patience window, it does not defeat it. Stopped via `Stop-HeartbeatSidecar`/`stop_heartbeat_sidecar` after each CLI invocation and from the Ctrl+C/exit-handler paths. Cleanup waits are bounded: Bash checks its own running/stopped job table, gives the tracked helper 2s after TERM then 2s after KILL, and never waits unconditionally on a live helper. PowerShell runs the exact tracked job's synchronous `StopJob` in one retained asynchronous runspace and waits at most 2s per call; it never force-removes a nonterminal job. A timeout warns `MOE_HEARTBEAT_STOP_TIMEOUT`, preserves the job/PID (and pending stop operation), and refuses to start a duplicate sidecar; post-flight can proceed. No peer process/group is signalled and no task or lease is released by this cleanup. Bash escalation is explicitly logged as `MOE_HEARTBEAT_STOP_ESCALATED`. A `Start-Job` child is a real separate process, so an unresolved timeout is not proof it has exited. On a `reattachRequired` answer (`attempt-reconciling`, after a daemon restart) the sidecar reattaches the attempt the answer names, reading its `taskId`/`generation` from `.moe/attempts/<id>.json` (contract: `moe.heartbeat` in `docs/MCP_SERVER.md`). Architect/QA/governor seats also export the runner identity as `MOE_RUNNER_PROCESS_STARTED_AT`/`MOE_RUNNER_HOST`, which `moe-proxy` stamps onto in-session `claim_next_task` calls so those attempts reattach too; a worker seat unsets both (its wrapper finalizes only its own claim's attempt). Opt out via `MOE_DISABLE_HEARTBEAT=1`.
- **Hot reload**: at the loop top (after the poll sleep, before dispatch), a changed wrapper sha256 reloads once per hash (sh `exec`, ps1 in-process supervisor), deregistering with reason `wrapper_restart`. Only **committed bytes** reload: the file must be tracked in the wrapper's own checkout, never the project's, and match HEAD (`git ls-files --error-unmatch`, then `git diff --quiet HEAD`). Uncommitted edits defer with one `[INFO] MOE_WRAPPER_RELOAD_DEFERRED: wrapper has uncommitted edits` line per hash; the seat keeps serving current bytes and reloads once they are committed (a checkpoint/wip commit counts). A failed check (no git, not a work tree — including a plugin-bundled copy — unborn HEAD, unreadable index) also defers, with `[WARN] MOE_WRAPPER_RELOAD_DEFERRED: cannot confirm the wrapper bytes are committed (...)`, never ending or deregistering the seat; relaunch such a seat by hand to load new bytes. Committed bytes failing `bash -n` or ParseFile are refused once per hash (`MOE_WRAPPER_RELOAD_REFUSED`). The sh main loop and post-loop tail are parsed as ONE group (`{` before the loop, `exit` and `}` after the tail): once the loop starts, bash never reads moe-agent.sh again. Before task-f31d415d, an in-place rewrite (same inode: editor save, apply_patch) made a seat whose loop ended read new tail bytes from its stale saved offset. Wrapper saves must not rely on in-place rewrites being safe for older seats: earlier bytes still read the tail from disk, and launch code above the loop is still parsed incrementally. Write the whole file elsewhere on the same filesystem, `bash -n` it, then one `mv -f` over the target; running seats keep the old inode. PowerShell parses the whole file, so ps1 needs no group. Tests: the four `[hot reload*]` arms of `postflight.{sh,ps1}` and the sh-only `[stale offset]` arm of `postflight.sh`.
- **Execution identity** (CQ-F09 to CQ-F12a; `moe-agent.{sh,ps1}`; the proxy side, with its validity rules and refusals, is in `packages/moe-proxy/README.md`): every iteration exports `MOE_SESSION_ID` = `<workerId>@<preflight-iso>`, the same id `moe.record_commit` takes as `sessionId`. The pre-flight `get_context` is the one served read: its args are `{taskId}`, plus `sessionId` when `MOE_SESSION_ID` is set. After the pre-flight claim (a fresh claim, or the held task of a resume), `pin_attempt_identity` (sh) / `Set-MoeAttemptIdentity` (ps1) export `MOE_ATTEMPT_ID` + `MOE_ATTEMPT_GENERATION` only once the claim's attempt record verifies against the store. The pair is both-or-neither: any failure leaves both blank with `[WARN] Missing/stale attempt identity; candidate completion will fail closed.`, a resume refreshes it from the store, and the loop top resets it so no CLI inherits a previous task's attempt (a hot reload keeps env). Post-flight and adoption `get_context` reads are unserved: `moe_rpc_unserved` (sh) / `Invoke-MoeRpcUnserved` (ps1) blank `MOE_SESSION_ID` for that one call, so the proxy stamps no `sessionId` and they mint no receipt. `moe-proxy` stamps the identity onto `get_context`, `start_step`, `complete_step`, `complete_task`, `qa_approve` and `qa_reject` (CQ-V06a) and refuses a caller-substituted or malformed one, so the seat's CLI can never present its own. Codex and grok reach the proxy only through their written config, so both carry the identity keys too (see the MCP servers bullet).
- **Compaction window + keeper mod** (claude launches only): the wrapper sets `CLAUDE_CODE_AUTO_COMPACT_WINDOW` per role (worker 300000, qa 500000, architect/governor 600000) and records its own value in `MOE_COMPACT_WINDOW_DEFAULT`, so a hot reload (sh `exec`, ps1 in-process supervisor — both keep the env) re-derives it while an unmarked operator value wins; a bare `300000` counts as the pre-2026-10-09 wrapper default. It also appends `scripts/mods/moe-compaction-keeper` to `CLAUDE_CODE_PLUGIN_DIRS` (path-list, `:`/`;`; opt out `MOE_DISABLE_COMPACTION_KEEPER=1`): a Claude Code mod whose `session.compact` hook, for a seat's main transcript only (`MOE_WORKER_ID` set, no `agentId`), adds Moe keep-instructions to the summarizer and inserts a task snapshot (status, steps, DoD, last QA rejection) read from `.moe/workers/<id>.json` + `.moe/tasks/<taskId>.json` after the summary; any failure falls through to plain compaction. Test with `claude plugin test scripts/mods/moe-compaction-keeper`; the launcher blocks are covered by `scripts/tests/prompt-cache-launcher.test.mjs`. Both IDE bundles ship `scripts/mods/**` minus `*.test.ts` and the engine-written `.claude-plugin/types/`.
- **Claude account rotation** (claude launches only; helper `scripts/moe-account-lease.mjs`, wrapper-only tools `moe.lease_account`/`moe.report_account_usage` over the same one-shot proxy RPC as every other wrapper call): before each claude launch the wrapper leases an account (`MOE_ACCOUNT_ROTATION=off` skips it; a set `CLAUDE_CODE_USE_{BEDROCK,VERTEX,FOUNDRY}` stands rotation down) and runs claude with `CLAUDE_CONFIG_DIR=<configDir>`, `MOE_ACCOUNT_ID` and `MOE_ACCOUNT_SAMPLE_FILE` set and `ANTHROPIC_API_KEY`/`ANTHROPIC_AUTH_TOKEN`/`CLAUDE_CODE_OAUTH_TOKEN` removed, in the CLI's own subshell/process only. The wrapper opens one file inside a config directory, and only for an interactive seat: `moe-account-lease.mjs trust` sets `projects[<key>].hasTrustDialogAccepted` in the leased account's `.claude.json`, where `<key>` is what Claude's own folder-trust dialog writes for the launch directory (its git top-level, else the directory, `/`-separated on Windows; the directory and its real path are set too). It writes under Claude's own `.claude.json.lock`, re-reads under it, changes nothing else and reads the key back. Nothing from the file is printed or sent, `.credentials.json` is never opened, and headless `-p` seats, which never see the dialog, are unchanged (human sign-off 2026-10-26, task-7a0b1881). From `claude auth status --json` the wrapper takes only the exit code and `authMethod`. Usage reaches the daemon through the sample file, written by the stream parser from `rate_limit_event` or, on an interactive seat, by a `--settings` statusLine (`moe-account-lease.mjs statusline`), and sent after the run and by the heartbeat sidecar mid-run; a bash interactive seat also gets `--mcp-config <project>/.mcp.json`, because a fresh config dir holds none of the operator's `.mcp.json` approvals (`-p` connects them unasked). After a failed run, a refused sample the daemon took prints `MOE_ACCOUNT_REFUSED`; any other failure probes the sign-in and prints `MOE_ACCOUNT_SIGNED_OUT state=signed_out|other`. Both relaunch at once on the next account, with no launch-failure backoff, the resume attempt given back, even under `--no-loop`, unless the daemon hands back the account it just moved off and that fails again (the launch-failure classes then apply). Every signed-in account spent: `MOE_ACCOUNT_WAIT`, sleeping the daemon's `retryInSec` capped at `MOE_ACCOUNT_RETRY_SEC` (default 300), the task held. An interactive seat's lease then runs the trust step (sh: the project, where claude runs; ps1: the launcher's cwd, which must be the project or inside it): `MOE_ACCOUNT_TRUST_GRANTED` when it set the key, nothing when the key was already set. When it cannot set it (no `.claude.json`, not a regular file or JSON object, over 16 MiB, Claude's lock held past 2 s, a failed rewrite or read-back, a launch directory outside the project), the seat never launches into the dialog: `MOE_ACCOUNT_UNTRUSTED account=<id> project=<path> (<reason>)`, one `#general` escalation per account per lease loop naming the account and the project (never the folder), a `MOE_ACCOUNT_RETRY_SEC` sleep with the task held, then a fresh lease. A trust helper that fails outright launches unrotated. Anything else launches unrotated (`MOE_ACCOUNT_LEASE_UNAVAILABLE`). An interactive claude seat whose loop relaunches it (`CLAUDE_INTERACTIVE` and `LOOP_ENABLED`, ps1 `$claudeInteractive` and `$loopEnabled`) also gets `scripts/mods/moe-account-switch` appended to `CLAUDE_CODE_PLUGIN_DIRS` (opt out `MOE_DISABLE_ACCOUNT_SWITCH_MOD=1`). The account switch needs `MOE_WORKER_ID` and `MOE_ACCOUNT_ID`, and only a leased launch sets `MOE_ACCOUNT_ID`. It adds `acceptsAccountSwitch` to `submit_plan`/`chat_wait`, so the daemon can move the seat between tasks. Once a moe reply carries `accountSwitch` (or claude stops at the limit, 100%), the mod refuses `claim_next_task`/`wait_for_task`/`chat_wait`/`start_step`. It runs `/exit` 10 s after the main turn ends, and the loop relaunches the seat on the next account. Where that loop also claims for the seat (auto-claim, not a governor) the wrapper sets `MOE_SESSION_ENDS_WHEN_IDLE` (cleared otherwise), and the mod also ends a session whose seat holds no task once a main turn ends uninterrupted (its `.moe/workers/<id>.json` record, read-only; an unreadable record keeps the session): nothing left to plan, the architect session cap, a notification-only session. The wrapper then launches only once a task is claimable. The daemon's `END_SESSION` handoff needs only `MOE_WORKER_ID`, so it works on an unrotated seat too: a moe reply whose top-level `sessionHandoff.action` is `END_SESSION` for this seat's worker id (`report_blocked` freeing the seat, or a `claim_next_task`/`wait_for_task` refusal over a resource-held task), in a session that draws on a surface (never a `-p` run), gets the same four-tool refusal and the same `/exit` 10 s after the main turn ends; the loop then relaunches the seat for its next task. Tests: `scripts/tests/moe-account-lease.test.mjs` (the helper, plus the trust step of both launchers' real lease loops on every engine), `[accounts]` in `postflight.{sh,ps1}` (the sh interactive run seeds an untrusted `.claude.json`), `claude plugin test scripts/mods/moe-account-switch`, and the launcher block in `prompt-cache-launcher.test.mjs`.
- **MCP servers for spawned agents** are built entirely by `scripts/moe-agent.{ps1,sh}` (the daemon schema has no MCP field), per CLI: `claude` gets a temp `--mcp-config` (PowerShell) or `~/.config/claude/mcp_servers.json` merge + `$PROJECT/.mcp.json` (bash); `codex` gets `.codex/config.toml` (`[mcp_servers.*]`); `gemini` gets `.gemini/settings.json` (`mcpServers`); `grok` gets `.grok/config.toml` (the same `[mcp_servers.*]` TOML as codex but **no top-level keys** — a grok project config may only carry `[mcp_servers.*]`/`[plugins]`/`[permission]`/`[mcp]` — with `MOE_WORKER_ID = "${MOE_WORKER_ID:-}"` written literally because grok expands `${VAR:-default}` per process (likewise `MOE_RUNNER_PROCESS_STARTED_AT`/`MOE_RUNNER_HOST`, the execution identity `MOE_SESSION_ID`/`MOE_ATTEMPT_ID`/`MOE_ATTEMPT_GENERATION` and the seat's CLI type `MOE_WORKER_TYPE`, each written as a literal `KEY = "${KEY:-}"` line, so an unset or blank value reaches `moe-proxy` as unset; codex, which hands an MCP server only the env its table names, gets all seven in its per-seat `-c mcp_servers.moe=…` override, filtered to the keys that are set: `MOE_SESSION_ID`, then the attempt pair, then `MOE_WORKER_TYPE`, then `MOE_WORKER_ID` and the runner keys — the ps1 override emits the pair both-or-neither); the wrapper also sets `GROK_CLAUDE_MCPS_ENABLED=0`/`GROK_CURSOR_MCPS_ENABLED=0` so grok stops auto-merging `~/.claude.json` and `.cursor/mcp.json` on top of it — a project `.mcp.json` can still be merged, `grok inspect` shows each server's origin — plus `GROK_DISABLE_AUTOUPDATER=1`). Two more grok-only wrapper steps, both measured necessary 2026-09-05 (grok 1.0.13): the `moe` env table also pins `MOE_TOOL_NAME_STYLE = "underscore"` because grok silently drops any MCP tool whose name contains a dot (the daemon's `moe.<name>` — the server showed as connected with 0 tools, then "failed to connect"), so the proxy exposes `moe_<name>` in `tools/list` and maps the alias back on `tools/call`; and the wrapper pre-trusts the project in `~/.grok/trusted_folders.toml` (`Grok folder trust granted: <path>`), because grok refuses a project's `.grok/config.toml` MCP servers in an untrusted folder and a headless worker never sees the TUI's trust prompt. Grok reaches MCP tools only through its `search_tool`/`use_tool` dispatchers under qualified names (`moe__moe_<name>`, `serena__<tool>`); the wrapper's prompt says so. The grok `moe` entry also carries `tool_timeout_sec = 120` (`MOE_GROK_MCP_TOOL_TIMEOUT_SEC`) with a 720s `tool_timeouts` override for the three blocking long-polls — grok's 6000s default let one lost (undecodable) response park a call for minutes. **All four CLIs** inject the `moe` proxy server **and** a **Serena** server (LSP symbol navigation/editing + project memory) pinned to the project (headless — no dashboard/GUI), giving every role exact cross-file code intelligence and shared memory instead of whole-file reads. The codex and grok `moe` entries get `startup_timeout_sec` 120 (override `MOE_CODEX_MCP_STARTUP_TIMEOUT_SEC` / `MOE_GROK_MCP_STARTUP_TIMEOUT_SEC`; codex's 30s default loses the race against a supervised daemon restart), and because both TOML writers run **before** daemon host probing, WSL runs upsert the discovered `MOE_DAEMON_HOST` into `[mcp_servers.moe.env]` after discovery — so the written config stays self-contained even if the CLI doesn't forward the wrapper's environment to spawned MCP servers. Serena's project root is `serenaProject` in `<project>/.moe-agent.json`, else `MOE_SERENA_PROJECT`, else the Moe project root (the override exists for multi-repo workspace roots); its `--context` is `claude-code`/`codex`/`agent`/`agent` for claude/codex/gemini/grok. Serena is resolved from `MOE_SERENA_PATH` or `%USERPROFILE%\.local\bin\serena.exe`/`~/.local/bin/serena` and **no-ops if not installed** (`uv tool install -p 3.13 serena-agent`); the codex/gemini/grok writers are idempotent (re-runs don't duplicate the `serena` entry). To add more MCP servers for agents, extend these two scripts — there is no other hook.
