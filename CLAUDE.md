# CLAUDE.md

This file provides guidance to Claude Code (claude.ai/code) when working with code in this repository.

## Project

Moe is an AI Workforce Command Center — IDE plugins + a Node daemon that orchestrate AI agents through a task lifecycle (BACKLOG → PLANNING → AWAITING_APPROVAL → WORKING → REVIEW → DONE). The lifecycle has back-edges: `qa_reject` sends REVIEW → WORKING, auto-flipping to PLANNING after 3 reopens or when the same DoD item fails twice; in CONTROL mode a governor plan-critique `block` verdict also flips a task back to PLANNING. A side-state `BLOCKED` (not agent-claimable; display-mapped into the Working column) parks a PLANNING/WORKING/REVIEW task on an external blocker via `report_blocked` — a non-resource block reported by the assignee (or on an unassigned task) **frees the seat** (task unassigned, worker → IDLE to claim other work; the wrapper checkpointed the bytes at block time), while a `resourceId` block — or a third-party/workerId-less block on an assigned task — keeps the seat parked (grant-return path / never yank a live worker). Auto-unblock back to `blockedFromStatus` is dual: the shared-resource lease grant, or every `blockedOnTaskIds` target reaching DONE/ARCHIVED (`report_blocked` accepts the ids and also auto-parses `task-…` ids from the reason; event-driven with a sweep backstop; ids that are ALL already DONE/ARCHIVED at report time do **not** block — `dependenciesSatisfied:true`, continue; an id that would close a dependency cycle over `dependsOn ∪ blockedOnTaskIds` is dropped with a warning + #governors alert, and `set_task_dependencies` rejects one outright); otherwise `unblock_worker { resolveBlocks: true }` or `set_task_status` clears the block — a plain `unblock_worker` only frees the worker seat (the task stays BLOCKED with its `blockedReason`). JetBrains is the primary IDE — implement and test JetBrains changes first; VS Code lags and workers tend to over-index on it, so push back and prioritize JetBrains parity.

```
JetBrains/VS Code Plugin ── ws://…/ws ──▶ Moe Daemon ◀── ws://…/mcp ── moe-proxy ◀── agent CLI (MCP stdio)
                                            │
                                            ▼
                                         .moe/  (source of truth)
```

The daemon is the sole writer of `.moe/` **runtime state** (tasks, epics, workers, teams, proposals) — agents and humans must never edit `.moe/` by hand; go through `moe.*` MCP tools. The IDE plugins do, however, write to `.moe/` outside that invariant: they scaffold `.moe/` when missing, force-sync bundled role docs/skills into it on connect, and delete `.moe/daemon.json` when stale.

Roles: **architect** plans (`submit_plan`), **worker** codes per-step, **QA** reviews (`qa_approve`/`qa_reject`), **governor** oversees the fleet (never claims tasks). Humans gate transitions unless approval mode is relaxed.

## Build

```bash
cd packages/moe-daemon && npm install && npm run build   # prebuild generates init + skill files
cd packages/moe-proxy  && npm install && npm run build
cd moe-jetbrains       && ./gradlew buildPlugin           # zip → moe-jetbrains/build/distributions/
cd moe-jetbrains       && ./gradlew runIde                # sandbox IDE for dev
cd moe-vscode          && npm install && npm run package  # .vsix via vsce (compile/watch = typecheck only; no build script)
```

Both IDE plugin builds hard-fail unless daemon AND proxy each have `dist/` **and** `node_modules/` — npm install + build both first. Role-doc/skill edits reach IDE users only through a plugin rebuild (they're bundled into the plugin, then force-synced into each project's `.moe/`).

Windows full install (daemon + proxy + JetBrains plugin): `.\scripts\install-all.ps1`

## Run

The daemon default port is **9876** (override `--port` or `MOE_DEFAULT_PORT`; auto-scans the next 50 if taken). It binds `127.0.0.1` unless `--host`/`MOE_BIND_HOST` says otherwise (recorded as `bindHost` in daemon.json when non-loopback). Project resolves from `--project`, else `MOE_PROJECT_PATH`, else cwd. Endpoints: `ws://localhost:<port>/ws` (plugins), `ws://localhost:<port>/mcp` (proxy), HTTP `GET /health`. Clients discover the port from `.moe/daemon.json` (written by the daemon): the proxy retries a missing file for ~5 min (survives supervised restarts) but exits immediately on a project-path mismatch — the check treats `D:\path` and `/mnt/d/path` as the same project, and `MOE_DAEMON_HOST` overrides the proxy's connect host (both exist for **WSL agent mode**: the JetBrains Agents menu toggle "Run Agents in WSL" spawns the daemon with `--host 0.0.0.0` and launches agents via `moe-agent.sh` with `/mnt/` paths; the sh pre-flight detects a Windows-owned daemon.json by its drive-letter projectPath, probes `/health` over loopback then the WSL gateway instead of `kill -0` — a Windows PID is invisible in WSL — and refuses to delete daemon.json or start a duplicate daemon when the probe fails; requires node + the agent CLI installed inside the distro).

```bash
node packages/moe-daemon/dist/index.js start  --project <path>   # supervised (auto-restart, exp. backoff)
node packages/moe-daemon/dist/index.js init   --project <path>   # creates .moe/ then starts (keeps running)
node packages/moe-daemon/dist/index.js status --project <path>
node packages/moe-daemon/dist/index.js stop   --project <path>
node packages/moe-daemon/dist/index.js doctor --project <path>   # offline health check; exit 0 = green
node packages/moe-proxy/dist/index.js                            # MCP stdio bridge (agents)
scripts/moe-call.sh <tool> '<json-args>' --project <path>        # one-shot moe.* tool call from a terminal
```

`start` runs a supervisor that spawns the real daemon via the internal `_run` command and restarts it on crash (max 5 in 60s, backoff capped at 30s). Every daemon (re)start purges ALL worker records and releases their orphaned tasks (`purgeAllWorkers`) — agents must re-register after a restart. `doctor` does NOT require a running daemon — it walks `.moe/` checklist probes and exits 1 on any hard fail.

Launch agents via `scripts/moe-agent.{ps1,sh}` or a full team via `scripts/moe-team.{ps1,sh}`. Pre-flight: daemon autostart, per-CLI MCP-config writes, team/chat join, `claim_next_task` + `get_context` preload, and a `.moe/agents/*.md → .claude/agents/` subagent mirror (gated by `settings.enableAgentTeams`; sets `CLAUDE_CODE_EXPERIMENTAL_AGENT_TEAMS=1`). Skills are NOT synced by the wrapper — the daemon writes `.moe/skills/` at init and agents load them via their host's Skill tool. Post-flight: branch safety + landing (completion/checkpoint commit, rescue refs — see **Land on every exit** below). Agents run **in the project directory** — except the PowerShell `claude` launch, which runs in the launcher's cwd and binds to the project via `MOE_PROJECT_PATH` + a temp `--mcp-config` (codex/gemini/grok and all `.sh` launches `cd` into the project). Both launchers spawn claude `--print` one-shot and respawn a fresh CLI per task (PowerShell `-Interactive` / bash `--interactive` for the TUI; architect/governor default to interactive, worker/qa to one-shot — the per-task fresh context is what resets standards-compliance decay). `grok` (xAI Grok Build) follows the same role-based polarity: headless is `--prompt-file <temp file> --yolo --cwd <project> --no-auto-update --output-format plain` (the per-iteration prompt travels through a temp file — grok reads no stdin and has no `--prompt` flag), interactive passes a short pointer prompt positionally, and `-GrokExec`/`--grok-exec` forces headless; auth is `XAI_API_KEY` or a cached `grok login` (`~/.grok/auth.json`; a non-fatal `[WARN]` when both are missing). Model defaults: `claude-opus-5` for all roles (launched with `--effort max`), honored only by the `claude` CLI; codex instead gets `model_reasoning_effort = "xhigh"` written into its config.toml (override via `MOE_CODEX_REASONING_EFFORT`); grok gets `-m` only when a model is explicit (`-Model`/`--model`, `settings.models.{role}`, else `MOE_GROK_MODEL` — never the claude fallback) and `--effort` only from `MOE_GROK_EFFORT`; override the claude model via `-Model`/`--model` or `settings.models.{role}`.

## Working in this repo

- **Never edit `.moe/` files by hand** — go through `moe.*` MCP tools (contracts in `docs/MCP_SERVER.md`). Most of `.moe/` IS tracked in git (project.json, tasks/, roles/, skills/): daemon-driven diffs in `.moe/tasks/*.json` are intentional — commit/review them, don't revert them as junk (the wrapper's landing commits stage the task's own `.moe/tasks/<taskId>.json` as a BOARD path, plus changed `.moe/epics/*.json` / `.moe/project.json` / non-live-peer task records, when `settings.commitBoardState` is on — the default; peers' live task records are never staged). Only the runtime subset (daemon.json, activity.log, workers/, memory/, messages/, teams/) is gitignored, as is root `.mcp.json` (machine-local absolute paths — never commit it).
- Commit messages follow Conventional Commits (`feat(scope):`, `fix(scope):`, `chore:` …); releases are SemVer with all package versions synced.
- **Adding/changing daemon MCP tools**: the only registry is `getTools()` in `packages/moe-daemon/src/tools/index.ts` — an unregistered tool is silently invisible to MCP. Tool dispatch is serialized through the global reentrant state mutex (McpAdapter and plugin WS handlers share it); a tool that parks for minutes must set `blocking: true` (currently `wait_for_task`/`chat_wait`/`wait_for_resource`) or it freezes every other tool fleet-wide.
- **Land on every exit** (`scripts/moe-agent.{ps1,sh}` post-flight — the wrappers are the only git actors; the daemon is state-only and never runs git). With `settings.autoCommit` on (default) every session exit that holds a task lands its bytes. A **worker** exit at `REVIEW`/`DONE` makes a *completion* commit (`feat|fix(task-<id>): <title>`) and pushes; any other exit (WORKING/BLOCKED/PLANNING/AWAITING_APPROVAL, or a failed status lookup → `status=UNKNOWN`) for worker/architect/qa makes a *checkpoint* commit (`wip(task-<id>): … [status=<S> role=<r> cli-exit=<N>]`; pushed per `settings.checkpointPush`, default on; off via `settings.checkpointCommits=false` or `MOE_DISABLE_CHECKPOINT=1`). Attribution is per task and pathspec-only (`:(literal)`; never `git add -A`/`-u`, never a bare `git commit`, no whole-tree fallback): a per-task baseline snapshot (`<gitdir>/moe/baseline/<taskId>.tsv`, taken at pre-flight, pruned after each landing, kept until DONE/ARCHIVED) plus `moe.get_commit_scope` tier every dirty path — **ASSERTED** (completed-step `modifiedFiles`, `declare_files`, prior commits — committed regardless of baseline), **PLANNED** (plan-declared; only if changed since baseline), **TOOL** (stream-json Edit/Write harvest, claude only), **MEASURED** (undeclared + changed; committed only when `attribution.undeclared` allows — default `'solo'` = no other live worker — else reported as `MOE_ATTRIBUTION_UNRESOLVED`), **PEER** (`MOE_ATTR_PEER_DECLARED` skip), **PREEXISTING** (`MOE_ATTR_PREEXISTING` skip — dirty before the task and untouched is never committed), **DENY** (`MOE_ATTR_EXCLUDED`: `.moe/**` except BOARD, `.mcp.json`, `.codex/**`, `.gemini/**`, `.grok/**`, `.claude/agents/**`, `.worktrees/**`, `attribution.exclude`), **BOARD** (own `.moe/tasks/<id>.json`). Landing = temp index + `commit-tree` + `update-ref` CAS (3 attempts; `MOE_COMMIT_FAILED_REF_CONTENTION` after), so peers' staged entries survive and git hooks do **not** run unless `settings.commitHooks=true` (then completion commits only use porcelain `git commit -- <specs>`; checkpoints stay plumbing). Gate-failed (`settings.qualityGate`, epic-final by default, `MOE_DISABLE_QUALITY_GATE=1` skips), peel-failed, commit-failed, ref-contention and Ctrl+C teardown never touch the branch: the bytes go to a **rescue ref** `refs/moe/rescue/<taskId>/<utc-ts>` (`MOE_RESCUE_REF` chat line; never pushed), the baseline is kept, and the next pre-flight of that task lands it as a checkpoint (`MOE_CHECKPOINT_RECOVERED`). Refusal codes `MOE_COMMIT_REFUSED_NO_OWNED_PATHS` / `MOE_COMMIT_REFUSED_OWNED_PATH_MISSING` keep their meaning; `MOE_COMMIT_NOTHING_TO_COMMIT` is the idempotent no-op. Every outcome is reported via `moe.record_commit` into `task.commits`. Branch safety: never commit on `main`/`master`/detached — peel onto literal `settings.consolidationBranch` else the shared `moe/work-<YYYY-MM-DD>` (not branch-per-task; existing non-default branches are reused).
- Approval modes (`CONTROL` default / `SPEED` / `TURBO`), `agentCommand`, `autoCommit`, `checkpointCommits`, `checkpointPush`, `commitBoardState`, `commitHooks`, `attribution.{undeclared,contested,exclude}`, `qualityGate`, `taskSizing`, `models.{role}`, and `enableAgentTeams` live in `.moe/project.json` `settings`.
- **Task-size + verification gates** (both tunable/removable only in code or settings — they exist because prompt-only rules measurably don't hold): `submit_plan` warns past 8 steps / 5 distinct affectedFiles and hard-rejects past 12 / 10 (`settings.taskSizing`; logic in `util/planSize.ts`) with "split via moe-epic-breakdown/SPIDR" guidance; `create_task` guardrails are **all advisory — creation never hard-fails** (columnLimits at creation, meta-titled-row consolidation, and `taskSizing.maxTasksPerEpic` default 40 emit warnings only; `workerId` resolves the creator's role for `createdBy` attribution); task `dependsOn` (set at `create_task`, edited via `set_task_dependencies` — the architect/governor escape hatch) gates **WORKING-status claims only** (planning proceeds; missing/deleted ids count as satisfied); `complete_task` requires `verification: { command, exitCode: 0, outputTail? }`, persisted on the task and surfaced to QA via `get_context` for re-run auditing, and persists `summary` as `completionSummary`; `qa_approve` requires a `summary` of what was verified (persisted as `reviewSummary`) and is a **soft commit gate**: it returns `warnings[]` (`NO-COMPLETION-COMMIT` when no completion commit is recorded since `reviewStartedAt` — the wrapper lands it seconds after REVIEW, so QA checks `task.commits` / `git show <sha>` first) plus `commitEvidence`, but always approves. `scripts/analyze-task-metrics.mjs` reports reopen/reject rates per plan-size bucket from `.moe/tasks/*.json` for tuning the thresholds (`--commits` buckets `feat|fix` / `wip` / `rescue` per task and lists unrecovered rescue refs).
- Dead-worker handling, three layers: every daemon (re)start purges all worker records and releases their tasks; graceful exits call `moe.deregister_worker` from the wrapper's exit trap (`moe-agent.{sh,ps1}`); and a dead **CLI** under a still-live wrapper (one-shot `--print` exits at end_turn, killing background jobs) self-heals via the wrapper resume path — `claim_next_task` returns `hasNext:false` + `alreadyAssigned` and the wrapper relaunches the CLI onto the held task with a RESUME prompt (cap `MOE_RESUME_MAX_ATTEMPTS`, default 5, then a one-time #general escalation and idle). There is deliberately **no idle-based auto-release for WORKING/PLANNING** (the old 30-min worker-liveness sweep was removed — it yanked tasks off long-running coders): a hard-crashed worker's task stays assigned until daemon restart, `moe.deregister_worker`, or a manual/governor `release_task` — and its uncommitted bytes are not lost either way: the persisted per-task baseline makes the next session of that task (including the BLOCKED-hold and resume-cap idle paths) land a recovery checkpoint before any CLI launches. Task claimability keys strictly on the owner being missing from the worker map or explicitly `DEAD` (`isTaskClaimable`) — **never on idle time for WORKING/PLANNING**: a worker quiet past the 120s `isWorkerAlive` presence window (display-only, for `list_workers`/`chat_who`) keeps its task. **REVIEW is the deliberate exception**: a QA owner silent past `reviewStaleTimeoutMs` (default 30 min, same default as `staleWorkerTimeoutMs`; both configurable per-project via `.moe/project.json` `settings`) has its REVIEW task released (unassigned, status stays REVIEW) so another QA can claim it — added because a hard-crashed QA with no graceful deregister isn't `DEAD` and would otherwise strand the task forever. Release routing (`nextStatusForRelease`, shared by every path): WORKING stays WORKING-unassigned so the next worker re-claims and resumes it (workers claim ONLY the WORKING column — BACKLOG is human-gated and invisible to agents), or →REVIEW if every step is already done; PLANNING/REVIEW stay put. The **blocked-timeout sweep is the one 'park' exception**: it routes in-flight tasks (PLANNING/WORKING/REVIEW) → BACKLOG deliberately, because the blocker is usually environmental and requeueing would claim-thrash the next agent into the same wall; humans un-park via `set_task_status` (BACKLOG→PLANNING/WORKING/REVIEW are all legal transitions). A dependency-waiting BLOCKED hold (`blockedOnTaskIds` set) under a timed-out worker is **unassigned but stays BLOCKED** (the auto-unblock only scans BLOCKED rows; a row left assigned to the timed-out corpse would be restored onto it — unclaimable and unprunable), and the dependency auto-unblock itself restores a still-assigned hold to its worker only while that worker exists, is not DEAD and still points at the task — else the task returns unassigned. The same sweep's stale-block `#governors` alert covers dep-less rows past `blockedTimeoutMs`, dep-waiting rows whose prerequisite is itself BLOCKED/BACKLOG (a cycle or a parked prerequisite — nothing auto-clears without a human), and dep-waiting rows past 2× the timeout. `claim_next_task`/`wait_for_task` hard-reject statuses outside PLANNING/WORKING/REVIEW — claiming a human-gated column (BACKLOG/AWAITING_APPROVAL/DONE) used to "succeed" without transitioning status and wedge the worker. `DEAD` workers are dropped from the UI and their records pruned once they own nothing.
- **Heartbeat sidecar** (`moe-agent.{sh,ps1}`): the wrapper blocks synchronously on the CLI subprocess for its whole runtime with zero interleaved activity, and `moe-proxy` opens a fresh connection per RPC call rather than holding one for the CLI's lifetime — so the daemon's only liveness signal is "did this worker call a moe.* tool recently." A long silent local step (a build, a full test run) can outlast `reviewStaleTimeoutMs` even while the CLI is still very much alive and about to call `qa_approve`/`qa_reject`, which would otherwise let the REVIEW self-heal above steal the task out from under a live session. The wrapper runs a background sidecar (PowerShell `Start-Job` / bash backgrounded subshell) alongside the blocking CLI call that pings the no-op `moe.heartbeat` tool on a timer (`MOE_HEARTBEAT_INTERVAL_SEC`, default 60s) to keep `lastActivityAt` fresh, bounded by `MOE_HEARTBEAT_MAX_DURATION_SEC` (default 2h) so a truly-hung CLI still eventually goes stale — this extends the self-heal's patience window, it does not defeat it. Stopped via `Stop-HeartbeatSidecar`/`stop_heartbeat_sidecar` after each CLI invocation, and also from the same Ctrl+C/exit-handler paths as `moe.deregister_worker` (a `Start-Job` child is a real separate process that outlives the wrapper unless explicitly stopped). Opt out via `MOE_DISABLE_HEARTBEAT=1`.
- **Shared resources** (`state/resourceStore.ts`, tools `acquire_resource`/`release_resource`/`list_resources`/`wait_for_resource` — the last is `blocking: true`): daemon-owned admission control for exclusive-use infra (a benchmark box, a staging DB) replacing per-project marker files + pid probes. Leases are **task-keyed** (survive CLI respawns AND the restart worker purge), persisted in `.moe/resources/<id>.json`, granted FIFO-by-task-priority; undeclared ids auto-create (capacity 1, `maxLeaseMs` 24h — override via `settings.resources`). `report_blocked` with a `resourceId` first tries the lease (free → granted, no block), else queues + flips the task WORKING/PLANNING/REVIEW → `BLOCKED` (`blockedFromStatus` remembered); the grant path flips it back and that single status write is what wakes the fleet. `BLOCKED` is not agent-claimable; `nextStatusForRelease` keeps it BLOCKED on requeue (restart must not un-block) and BACKLOG on park; the blocked-timeout sweep **skips** resource-waiting BLOCKED tasks (their bound is the lease reaper: expiry force-release + orphan cleanup + grant onward, same 5-min sweep). Wrappers suppress CLI relaunch for `alreadyAssigned{status:BLOCKED}` without burning resume attempts.
- Skills (`docs/skills/`) are mirrored into `.moe/skills/` at init and loaded per role; daemon `prebuild` regenerates the vendored init/skill file content.
- **MCP servers for spawned agents** are built entirely by `scripts/moe-agent.{ps1,sh}` (the daemon schema has no MCP field), per CLI: `claude` gets a temp `--mcp-config` (PowerShell) or `~/.config/claude/mcp_servers.json` merge + `$PROJECT/.mcp.json` (bash); `codex` gets `.codex/config.toml` (`[mcp_servers.*]`); `gemini` gets `.gemini/settings.json` (`mcpServers`); `grok` gets `.grok/config.toml` (the same `[mcp_servers.*]` TOML as codex but **no top-level keys** — a grok project config may only carry `[mcp_servers.*]`/`[plugins]`/`[permission]`/`[mcp]` — with `MOE_WORKER_ID = "${MOE_WORKER_ID:-}"` written literally because grok expands `${VAR:-default}` per process; the wrapper also sets `GROK_CLAUDE_MCPS_ENABLED=0`/`GROK_CURSOR_MCPS_ENABLED=0` so grok stops auto-merging `~/.claude.json` and `.cursor/mcp.json` on top of it — a project `.mcp.json` can still be merged, `grok inspect` shows each server's origin — plus `GROK_DISABLE_AUTOUPDATER=1`). Two more grok-only wrapper steps, both measured necessary 2026-09-05 (grok 1.0.13): the `moe` env table also pins `MOE_TOOL_NAME_STYLE = "underscore"` because grok silently drops any MCP tool whose name contains a dot (the daemon's `moe.<name>` — the server showed as connected with 0 tools, then "failed to connect"), so the proxy exposes `moe_<name>` in `tools/list` and maps the alias back on `tools/call`; and the wrapper pre-trusts the project in `~/.grok/trusted_folders.toml` (`Grok folder trust granted: <path>`), because grok refuses a project's `.grok/config.toml` MCP servers in an untrusted folder and a headless worker never sees the TUI's trust prompt. Grok reaches MCP tools only through its `search_tool`/`use_tool` dispatchers under qualified names (`moe__moe_<name>`, `serena__<tool>`); the wrapper's prompt says so. The grok `moe` entry also carries `tool_timeout_sec = 120` (`MOE_GROK_MCP_TOOL_TIMEOUT_SEC`) with a 720s `tool_timeouts` override for the three blocking long-polls — grok's 6000s default let one lost (undecodable) response park a call for minutes. **All four CLIs** inject the `moe` proxy server **and** a **Serena** server (LSP symbol navigation/editing + project memory) pinned to the project (headless — no dashboard/GUI), giving every role exact cross-file code intelligence and shared memory instead of whole-file reads. The codex and grok `moe` entries get `startup_timeout_sec` 120 (override `MOE_CODEX_MCP_STARTUP_TIMEOUT_SEC` / `MOE_GROK_MCP_STARTUP_TIMEOUT_SEC`; codex's 30s default loses the race against a supervised daemon restart), and because both TOML writers run **before** daemon host probing, WSL runs upsert the discovered `MOE_DAEMON_HOST` into `[mcp_servers.moe.env]` after discovery — so the written config stays self-contained even if the CLI doesn't forward the wrapper's environment to spawned MCP servers. Serena's project root is `serenaProject` in `<project>/.moe-agent.json`, else `MOE_SERENA_PROJECT`, else the Moe project root (the override exists for multi-repo workspace roots); its `--context` is `claude-code`/`codex`/`agent`/`agent` for claude/codex/gemini/grok. Serena is resolved from `MOE_SERENA_PATH` or `%USERPROFILE%\.local\bin\serena.exe`/`~/.local/bin/serena` and **no-ops if not installed** (`uv tool install -p 3.13 serena-agent`); the codex/gemini/grok writers are idempotent (re-runs don't duplicate the `serena` entry). To add more MCP servers for agents, extend these two scripts — there is no other hook.
